Runtime Directory Structure
---------------------------

The standard runtime directories for royalcraps are:

*  System-Wide Config: /etc/royalcraps/config.conf
   * Purpose: Default settings for all users (e.g., default bet limits, game rules).
   * Access: Read-only for users; writable by admins.
*  User-Specific Config: $XDG_CONFIG_HOME/royalcraps/config.conf (defaults to ~/.config/royalcraps/config.conf)
   * Purpose: User-customized settings (e.g., key bindings, display preferences).
   * Access: Read/write for the user.
*  Save Games: $XDG_DATA_HOME/royalcraps/saves/ (defaults to ~/.local/share/royalcraps/saves/)
   * Purpose: Store game state (e.g., chips, bet history).
   * Access: Read/write for the user.
*  Shared Data: /usr/share/games/royalcraps/
   *Purpose: Static assets (e.g., ASCII dice art, rule descriptions).
   *Access: Read-only for users.
*  Variable Data: /var/games/royalcraps/
   * Purpose: System-wide data like global high scores.
   * Access: Writable by the game (e.g., via games group).
*  Cache: $XDG_CACHE_HOME/royalcraps/ (defaults to ~/.cache/royalcraps/)
   * Purpose: Temporary data (e.g., precomputed animations).
   * Access: Read/write for the user.
*  Executable: /usr/games/royalcraps
   * Purpose: Game binary

if (getmouse(&event) == OK) {
    if (event.y == 0) { /* Table info click */ }
    else if (event.y == 1) { /* Roll history click */ }
    else if (event.y >= 2 && event.y < termRows - 2) { /* Table layout */ }
    else if (event.y == termRows - 2) { /* Player info click */ }
    else if (event.y == termRows - 1) { /* Command line */ }
}

6. Redraw Strategy

    Each zone redraws only when its data changes.

    Table layout will update more often (bets moving, dice animation, etc.).

    Command line is interactive — redrawn on every keystroke.

This makes performance snappy even in 80×24.

    Catch SIGWINCH

    Redraw everything

Undo Capability
---------------

Supported (stack-based undo, limited to bets)

* Scope: only bet state (no configuration, no gameplay state, no rolls).
* Granularity: one atomic bet change = one undo step.
* Kinds of changes:

  * new bet placed
  * existing bet modified (amount, odds, flags)
  * bet removed

* Ordering: last-in, first-out (classic undo stack).
* Lifetime: undo history is cleared after each roll (so you can only undo the current betting decisions before the dice are rolled).

Not supported (explicit exclusions)

* Undoing out of order changes (no random-access undo).
* Redo.
* Anything outside of bets (like table config, game options).

Implications for implementation

* Each action on bets needs to push a reversible “snapshot” (or command
  object) onto an undo stack.  e.g. "BetAdded {id, betData}",
  "BetModified {id, oldAmount, newAmount}", "BetRemoved {id, betData}".
* When you pop and execute an undo, you restore the prior state of that
  bet (or remove it, or re-add it).
* Clear the undo stack at the end of each roll → ensures betting
  decisions are isolated to the roll cycle.

Menus
-----

Menu behaviors:
* Default for menu visibility is off.
* SPACEBAR toggles menu visbility for the currently active menu.
* SPACEBAR key is actionable from any menu.
* Enabling visibility from within a menu affects only that menu, it
  does not enable visibility up and down the chain of menus.
* Most menu entries are fixed, however some menus are dynamically
  built to present current bets and choices to the user.

ESC quits the current menu, visible or not, and control is
given back to the parent menu.

The top most and starting menu is the Betting Menu.  All other menus are
reachable from this menu.  Since the game opens up on the Craps Table
with players ready to go, this makes sense.  I don't think I need
accelerator keys like VIM uses, however, I do use '.' to bring up the
Control Menu.

With respect to the popup subwindow for entering bet amounts, it has some

focused on a particular bet and amount, it is natural to use it to help
configure some automatic behaviors.

The Amount Entry subwindow will support two menu entries
such that if selected it uses the current entry value for:

* setting the auto fill value for the current bet type, to be used for
  default filling future bets of this type with the given amount.
      
* using the current bet type and amount to configure a quick bet. A

Quick Bets

When building a menu of quick bet choices, there will also need to be a
controller function to obtain the current quick bets. This will also be
necessary when editing quick bets via the configuration menu.

For CUI, when a quick bet is set from the DialogAmountEntry, it is
automatically assigned the next available slot in the quick bet
list. I'm thinking the slots are associated with a single digit number
starting at '1', so therefore 1,2,3,4,5,6,7,8,9. If we want to support
more than just 9 quick bets then slots beyond 9 would be associated with
single alpha character 'a','b','c' and so on. But in the spirit and
purpose of quick bets I think a max of 9 is probably sufficient and will
satisfy user convenience.

The QuickBet class in controller has these responsibilities:

* maintains a list of quick bets. std::list or std::vector is fine
* works off of indexes, not key mappings
* UI is responsible for presenting key mappings to quick bets if
  any. Could be numbers or alphas or just highlighted entry or pointer
  position.
* applyQuickBet(size_t index);
* setQuickBet(BetName betName, size_t pivot, bool oddsBet, Gen::Money amount);
* deleteQuickBet(BetName betName, size_t pivot, bool oddsBet); shift entries if necessary, no empty slots
* deleteQuickBet(size_t index); shift entries if necessary, no empty slots
* getQuickBets() - returns a vector of quick bet entries

Auto Fill

The AutoFill class in controller has these responsibilities:

* maintains a list of auto fill bets. std::vector is fine
* amount = getAutoFill(BetName betName, size_t pivot, bool oddsBet);
* setAutoFill(BetName betName, size_t pivot, bool oddsBet, Gen::Money amount);
  replaces amount if the entry already exists
* getAutoFills() - returns the vector of auto fill entries - so
  it can be edited via configuration menu.
* deleteAutoFill(BetName betName, size_t pivot, bool oddsBet); shift entries if necessary, no empty slots
