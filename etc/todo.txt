Runtime Directory Structure
───────────────────────────

The standard runtime directories for royalcraps are:

*  System-Wide Config: /etc/royalcraps/config.conf
   * Purpose: Default settings for all users (e.g., default bet limits, game rules).
   * Access: Read-only for users; writable by admins.
*  User-Specific Config: $XDG_CONFIG_HOME/royalcraps/config.conf (defaults to ~/.config/royalcraps/config.conf)
   * Purpose: User-customized settings (e.g., key bindings, display preferences).
   * Access: Read/write for the user.
*  Save Games: $XDG_DATA_HOME/royalcraps/saves/ (defaults to ~/.local/share/royalcraps/saves/)
   * Purpose: Store game state (e.g., chips, bet history).
   * Access: Read/write for the user.
*  Shared Data: /usr/share/games/royalcraps/
   *Purpose: Static assets (e.g., ASCII dice art, rule descriptions).
   *Access: Read-only for users.
*  Variable Data: /var/games/royalcraps/
   * Purpose: System-wide data like global high scores.
   * Access: Writable by the game (e.g., via games group).
*  Cache: $XDG_CACHE_HOME/royalcraps/ (defaults to ~/.cache/royalcraps/)
   * Purpose: Temporary data (e.g., precomputed animations).
   * Access: Read/write for the user.
*  Executable: /usr/games/royalcraps
   * Purpose: Game binary

4. Mouse Click Mapping (Maybe support)

Ncurses mouse events give you y and x coordinates.
You can identify where the click happened:

MEVENT event;
if (getmouse(&event) == OK) {
    if (event.y == 0) { /* Table info click */ }
    else if (event.y == 1) { /* Roll history click */ }
    else if (event.y >= 2 && event.y < termRows - 2) { /* Table layout */ }
    else if (event.y == termRows - 2) { /* Player info click */ }
    else if (event.y == termRows - 1) { /* Command line */ }
}

6. Redraw Strategy

    Each zone redraws only when its data changes.

    Table layout will update more often (bets moving, dice animation, etc.).

    Command line is interactive — redrawn on every keystroke.

This makes performance snappy even in 80×24.

7. Resizing (Maybe support)

    Catch SIGWINCH

    Recalculate all subwindow dimensions

    Redraw everything

    If below minimum, pause game with resize prompt

Undo Capability
───────────────

Supported (stack-based undo, limited to bet actions)

* Scope: only bet state (no configuration, no gameplay state, no rolls).
* Granularity: one atomic bet change = one undo step.
* Kinds of changes that can be undone:

  * new bet placed
  * existing bet modified (amount, odds, flags)
  * bet removed

* Ordering: last-in, first-out (classic undo stack).
* Lifetime: undo stack is cleared after each roll, so you can only 
  undo the current betting decisions before the dice are rolled.

Not supported (explicit exclusions)

* Undoing out of order changes (no random-access undo).
* Redo.
* Anything outside of bets (like table config, game options).

Implications for implementation

* Each action on bets needs to push a reversible “snapshot” command
  object onto the undo stack.  e.g. "BetAdded {id, betData}",
  "BetModified {id, oldAmount, newAmount}", "BetRemoved {id, betData}".
* When an undo is executed, the prior state of that bet is restored.

Menus
─────

Menu behaviors:

1. Top-level modes replace or overlay the current table view.
2. Popup menus overlay the current view.
3. A popup owns its child popup/dialog.
4. ESC closes the current popup.
5. A successful action closes the current popup and returns
   according to its return policy.
6. Sticky parent remains available after child completion.
7. Ephemeral parent is discarded after child completion.
8. Dynamic menus contain only currently valid choices.
9. One-choice dynamic menus may be bypassed.
10. Top-level navigation is always available from the table.
11. Stats are full-screen modes.
12. Betting is the default command context on table views.

Once those rules are explicit, I think the implementation becomes
substantially easier—and, importantly, your individual
onPlayerXXX()/event handlers won't have to know anything about the
increasingly complicated popup hierarchy.

The game opens up on the Craps table view using the last
played Craps game. Player can go to the Control Menu to
switch to a different game player. The default opening view is the
Focused Player View.  Betting Menu key bindings are active.

Quick Bets

When building a menu of quick bet choices, there will also need to be a
controller function to obtain the current quick bets. This will also be
necessary when editing quick bets via the configuration menu.

For CUI, when a quick bet is set from the DialogAmountEntry, it is
automatically assigned the next available slot in the quick bet
list. I'm thinking the slots are associated with a single digit number
starting at '1', so therefore 1,2,3,4,5,6,7,8,9. If we want to support
more than just 9 quick bets then slots beyond 9 would be associated with
single alpha character 'a','b','c' and so on. But in the spirit and
purpose of quick bets I think a max of 9 is probably sufficient and will
satisfy user convenience.

* deleteQuickBet(size_t index); shift entries if necessary, no empty slots

Naming Clarity for UI->Model and Model->UI
------------------------------------------

UI->Model

*    Console/GUI screens issue readXxx() / cmdXxx() functions
*    readXxx() prefix for CrapsReader (queries model directly),
*    cmdXxx() prefix for CrapsEventEmitters (explicit "command"),
*    onXxx() prefix for CrapsEventHandlers (handles event to Model),

Model->UI

*    emitXxx() prefix for ViewEventEmitters (emits event to UI),
*    onXxx() prefix for ViewEventHandlers (handles event to UI),
*    showXxx() prefix for ViewInterface (UI updates for GUI/Console).
*    ConsoleView / GuiView implement showXxx() functions

This gives you a very clear split and the separation makes it impossible
to confuse an “event” with a “command.”

Class                   Prefix        Direction
----------------------  ------------  ------------------------
ViewCommands            emitXxx()     Model → notifies Controller, creates Event
ViewEventHandlers       onXxx()       Controller → processes Event, call ViewInterface
ViewInterface           showXxx()     Notifies View (Console or GUI)
CrapsCommands           cmdXxx()      UI → Controller (commands, createsEvent)
CrapsEventHandlers      onXxx()       Controller → processes Event, executes model command
CrapsReaders            readXxx()     UI → Controller (queries model directly read-only info)



pub/sub event for UI menus and friends
--------------------------------------

class UIEventBus {
public:
    using Handler = std::function<void(const GameEvent&)>;
    using SubscriptionId = size_t;

    static UIEventBus& instance() {
        static UIEventBus bus;
        return bus;
    }

    // subscribe: returns a token you can use to unsubscribe
    SubscriptionId subscribe(EventType type, Handler handler) {
        auto id = nextId_++;
        subscribers_[type].emplace_back(id, std::move(handler));
        return id;
    }

    void unsubscribe(EventType type, SubscriptionId id) {
        auto& vec = subscribers_[type];
        vec.erase(
            std::remove_if(vec.begin(), vec.end(),
                [id](auto& pair) { return pair.first == id; }),
            vec.end()
        );
    }

    void publish(const GameEvent& ev) {
        auto it = subscribers_.find(ev.type());
        if (it != subscribers_.end()) {
            for (auto& [id, handler] : it->second) {
                handler(ev);
            }
        }
    }

private:
    size_t nextId_{0};
    std::unordered_map<EventType,
        std::vector<std::pair<SubscriptionId, Handler>>> subscribers_;
};


Menus use it like this:

class MenuBetting {
public:
    void onActivate() {
        subId_ = UIEventBus::instance().subscribe(
            EventType::ViewErrorDialog,
            [this](const GameEvent& ev) {
                if (ev.correlationId == myCorrelationId_) {
                    showError(ev.message);
                }
            }
        );
    }

    void onDeactivate() {
        UIEventBus::instance().unsubscribe(EventType::ViewErrorDialog, subId_);
    }

private:
    UIEventBus::SubscriptionId subId_{0};
};
