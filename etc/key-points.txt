This is a single player Craps game, with up to 5 addtional
fake "buddy" players.

A player can select the table he wants to play on from a choice of
tables delivered with the game. Table switching can take place during
runtime. Maybe in the future, tables can be created/edited with the game
UI. Craps tables have their own table rules to mimic different rules
at various casinos around the world.

A player can select the buddy players he wants to join the table
from a choice of buddies delivered with the game. Maybe in the future,
buddies can be created/edited with the game UI.

A player can create a new Player and switch to a different players
at runtime.

When the player quits the game, the session is saved. When the player
starts another session, it picks up where the last session left off.
There is no "save now" option or disabling of the save operation.

When the game starts, the default player is the player of the last
session. It is up to the player to runtime switch to a different player
or create a new one if they want. A fresh game install uses the default
player packaged with the game.

Development is C++17

Using ncurses for CUI. Haven't yet selected GUI library.

Development uses Podman containers for compiler tools and documentation
tools. Containers are assembled using Makefile commands available in the
tools folder. For the build container, the strategy and logic keeps
the container around after a build. It does not exit.

Containers access source code directly on the host computer using
container workspaces. No code is copied into containers. Build artifacts
are written directly to the host "_build" tree.

Using various external libraries. Using Conan library as a consumer.

Using CMake for compilation only. A top level Makefile system
drives the overall build.

There is a single "_build" folder at the top of the work tree. It
branches into a debug and production tree. Debug and production builds
are supported simultaneously without reconfiguring CMake or Conan.
Top level Makefile offers commands for "make debug", "make prod", and
"make both".

Doctest is used for unit-tests.

The program design conforms to a somewhat relaxed MVC architecture.

The View interface consists of:

* Events via the one and only EventManager instance.

* GameEvents are used by the Model - for publishing only, Controller -
  for publishing and subscribing, and View - for publishing and
  subscribing.

* CrapsReaders interface, allowing the View to directly obtain
  model information for timely population of dynamic menus and to
  avoid heavyweight code duplication.

Using shared GameEvents and the CrapsReader interface is what is meant
by "relaxed" MVC design.

The program makes use of multiple threads. All threads are static -
initialized once and remain for the life of the program.

There is no formal database, just a number of persistent files, all
YAML.

There is no networking.

First phase is to implement a console user interface (CUI) version of
Royal Craps. This is used primarily to prove out the model and UI
interactions.

Future development will implement a 2D GUI with audio and animation.

The game supports command line options to select CUI or GUI (when
available).

This is currently being developed to run on only Linux platforms,
although I might reconsider that in the future.

Here's the CUI screen the player works with. There's an All Players View
and a One Player View. The player can toggle between these.

Table layout has three sections for bets. Each section has a list of bets
along with an indication of which player has made that bet. Within each
section, there are 6 columns of o's, one for each player (up to 6 players)
indicating if a player has made a bet.  o's in each column are color
coded to agree with assigned color of a player.  o's do not appear in a
column unless there's a bet for it on the table.  For passline, come,
dontpass, and dontcome bets, if the player has also made an odds bet,
then instead of an "o", a bullet or filled in "o"is shown. Notice a
header row over the columns; has the first initial of the player's name,
(in this example 5 players Nathan, Arthur, Paige, Lenny, Winnifred),
also color coded over their column.
