Startup Behavior (Doing This)
─────────────────────────────

First Running
    missing last saved game
    straight to ScreenCrapsTable
    player is given the name "Unamed"
    player bank is 10,000
    default table "Las Vegas Daytime"
    game over -> auto saved under "Unamed"
    player can Control -> Configure -> Rename Player
        Current player is renamed
    player can Control -> Configure -> New Player
        Prompt for new player name
        Current player is saved
        player is given new name
        player bank is 10,000
        table is whatever table is in use
    player can Control -> Configure -> Choose Player
        first running, player list will be empty
        tell player "No other players to choose from at this time."

Second Running and Onward
    load last saved game
    straight to ScreenCrapsTable
    pick up where left off
    player can Control -> Configure -> Choose Player
        prompt for player to choose
        current player is saved
        newly choosen player is loaded along with his table
    player can Control -> Configure -> New Player
    player can Control -> Configure -> Rename

3. Subwindow Allocation in Code

Example in C++ (ncurses):

int termRows, termCols;
getmaxyx(stdscr, termRows, termCols);

if (termRows < 24 || termCols < 80) {
    endwin();
    std::cerr << "Terminal too small (need at least 80x24)\n";
    exit(1);
}

4. Mouse Click Mapping (Maybe support)

Ncurses mouse events give you y and x coordinates.
You can identify where the click happened:

MEVENT event;
if (getmouse(&event) == OK) {
    if (event.y == 0) { /* Table info click */ }
    else if (event.y == 1) { /* Roll history click */ }
    else if (event.y >= 2 && event.y < termRows - 2) { /* Table layout */ }
    else if (event.y == termRows - 2) { /* Player info click */ }
    else if (event.y == termRows - 1) { /* Command line */ }
}

6. Redraw Strategy

    Each zone redraws only when its data changes.

    Table layout will update more often (bets moving, dice animation, etc.).

    Command line is interactive — redrawn on every keystroke.

This makes performance snappy even in 80×24.

7. Resizing (Maybe support)

    Catch SIGWINCH

    Recalculate all subwindow dimensions

    Redraw everything

    If below minimum, pause game with resize prompt

Vocabulary with ncurses
───────────────────────

| Term               | Meaning                                                                  |
| ------------------ | ------------------------------------------------------------------------ |
| **Screen**         | An entire application-level UI screen                                    |
| **`stdscr`**       | ncurses' root `WINDOW*`                                                  |
| **`WINDOW`**       | ncurses' rectangular character buffer/object                             |
| **content window** | One of your `WINDOW*` areas used by a Screen                             |
| **subwindow**      | Preferably reserve for actual ncurses `subwin()`/`derwin()` windows      |
| **frame**          | Borders/dividers/junctions drawn around the Screen                       |
| **navigation bar** | Persistent application-level UI component                                |
| **popup**          | Temporary application-level UI component                                 |
| **dialog**         | Temporary application-level UI component requesting/displaying something |


| Term                | Use it for                                                                     |
| ------------------- | ------------------------------------------------------------------------------ |
| **`draw()`**        | The virtual entry point on `ViewSurface`                                       |
| **`drawBorders()`** | Drawing static/structural borders and junctions                                |
| **`populate()`**    | Filling a window with its complete current contents                            |
| **`update()`**      | Changing only dynamic data within an already-populated window                  |
| **`refresh()`**     | **Don't use as your application method name**; reserve it for ncurses concepts |

wrefresh(win); Take the contents of this WINDOW and make them appear on the physical terminal.
wnoutrefresh(win); Copy the contents of this WINDOW into the virtual screen (newscr) without actually updating the terminal yet.
doupdate(); actually updates the physical terminal based on the virtual screen.

draw = render entry point
drawBorders = structural rendering
populate = completely fill contents
update = incrementally change window contents
transfer = move window contents to the ncurses' virtual/backing screen

refresh = reserve for ncurses
doupdate = ncurses' final terminal update


Screen Drawing Rules
────────────────────

The full-screen layout/frame owns all borders, dividers, corners, and
junction characters. Content subwindows own only their interior
contents.

The persistent navigation bar owns its own rectangular area/window, but
its boundary is still drawn by the full-screen frame/layout.

So the ownership model looks like this, for example:

Screen
│
├── Frame/Layout
│     └── all borders, dividers, corners, junctions
│
├── Content windows
│     ├── TitleBar
│     ├── History
│     ├── Table
│     ├── Messages
│     ├── Animation
│     ├── House
│     └── Player
│
└── Navigation window
      └── navigation contents

Undo Capability
───────────────

Supported (stack-based undo, limited to bet actions)

* Scope: only bet state (no configuration, no gameplay state, no rolls).
* Granularity: one atomic bet change = one undo step.
* Kinds of changes that can be undone:

  * new bet placed
  * existing bet modified (amount, odds, flags)
  * bet removed

* Ordering: last-in, first-out (classic undo stack).
* Lifetime: undo stack is cleared after each roll, so you can only
  undo the current betting decisions before the dice are rolled.

Not supported (explicit exclusions)

* Undoing out of order changes (no random-access undo).
* Redo.
* Anything outside of bets (like table config, game options).

Implications for implementation

* Each action on bets needs to push a reversible “snapshot” command
  object onto the undo stack.  e.g. "BetAdded {id, betData}",
  "BetModified {id, oldAmount, newAmount}", "BetRemoved {id, betData}".
* When an undo is executed, the prior state of that bet is restored.

Menus
─────

Menu behaviors:

1. Top-level modes replace or overlay the current table view.
2. Popup menus overlay the current view.
3. A popup owns its child popup/dialog.
4. ESC closes the current popup.
5. A successful action closes the current popup and returns
   according to its return policy.
6. Sticky parent remains available after child completion.
7. Ephemeral parent is discarded after child completion.
8. Dynamic menus contain only currently valid choices.
9. One-choice dynamic menus may be bypassed.
10. Top-level navigation is always available from the table.
11. Stats are full-screen modes.
12. Betting is the default command context on table views.

Once those rules are explicit, I think the implementation becomes
substantially easier—and, importantly, your individual
onPlayerXXX()/event handlers won't have to know anything about the
increasingly complicated popup hierarchy.

The game opens up on the Craps table view using the last
played Craps game. Player can go to the Control Menu to
switch to a different game player. The default opening view is the
Focused Player View.  Betting Menu key bindings are active.

18. One architectural point I'd strongly recommend

Don't make your controller handlers responsible for understanding popup hierarchy.

In other words, avoid code like:

onOddsBet()
{
    ...
    if (onlyOneBet)
        ...
    else
        ...

    if (sticky)
        ...
    else
        ...
}

Instead, I'd let the UI/menu layer own:

Menu stack
Parent
Child
Return behavior
ESC
Sticky/ephemeral behavior

while the controller continues to deal with commands/events.

17. Your dynamic menus suggest a useful abstraction

You have quite a few:

Which Odds Bet
Which Place Number
Which Hardway
Which Player
Which Table
Which Quick Bet
Which Bet to Remove
Which Bet to Set Working
...

They're all variations on:

    Display a list of choices and invoke an action associated with the selected choice.

I'd be tempted to have a generic menu model along the lines of:

struct MenuItem
{
    char key;
    std::string text;
    std::function<void()> action;
};

with:

class PopupMenu
{
    std::string title;
    std::vector<MenuItem> items;
    bool sticky;
};

Then dynamically generated menus don't need special UI infrastructure.

The data that builds the menu is what changes.

That seems particularly compatible with your existing event architecture.

Suggestion:

    Let ESC always back out just one level (as you have now).

    But also allow b (or something) as a shortcut back to the Betting Menu, regardless of depth.
    This avoids “ESC fatigue.”

Quick Bets

When building a menu of quick bet choices, there will also need to be a
controller function to obtain the current quick bets. This will also be
necessary when editing quick bets via the configuration menu.

For CUI, when a quick bet is set from the DialogAmountEntry, it is
automatically assigned the next available slot in the quick bet
list. I'm thinking the slots are associated with a single digit number
starting at '1', so therefore 1,2,3,4,5,6,7,8,9. If we want to support
more than just 9 quick bets then slots beyond 9 would be associated with
single alpha character 'a','b','c' and so on. But in the spirit and
purpose of quick bets I think a max of 9 is probably sufficient and will
satisfy user convenience.

The QuickBet class in controller has these responsibilities:

* maintains a list of quick bets. std::list or std::vector is fine
* works off of indexes, not key mappings
* UI is responsible for presenting key mappings to quick bets if
  any. Could be numbers or alphas or just highlighted entry or pointer
  position.
* applyQuickBet(size_t index);
* setQuickBet(BetName betName, size_t pivot, bool oddsBet, Gen::Money amount);
* deleteQuickBet(BetName betName, size_t pivot, bool oddsBet); shift entries if necessary, no empty slots
* deleteQuickBet(size_t index); shift entries if necessary, no empty slots
* getQuickBets() - returns a vector of quick bet entries

Auto Fill

The AutoFill class in controller has these responsibilities:

* maintains a list of auto fill bets. std::vector is fine
* amount = getAutoFill(BetName betName, size_t pivot, bool oddsBet);
* setAutoFill(BetName betName, size_t pivot, bool oddsBet, Gen::Money amount);
  replaces amount if the entry already exists
* getAutoFills() - returns the vector of auto fill entries - so
  it can be edited via configuration menu.
* deleteAutoFill(BetName betName, size_t pivot, bool oddsBet); shift entries if necessary, no empty slots

*    readXxx() prefix for CrapsReader (queries model directly),
*    cmdXxx() prefix for CrapsEventEmitters (explicit "command"),
*    onXxx() prefix for CrapsEventHandlers (handles event to Model),

Model->UI

*    emitXxx() prefix for ViewEventEmitters (emits event to UI),
*    onXxx() prefix for ViewEventHandlers (handles event to UI),
*    showXxx() prefix for ViewInterface (UI updates for GUI/Console).
*    ConsoleView / GuiView implement showXxx() functions

This gives you a very clear split and the separation makes it impossible
to confuse an “event” with a “command.”

Class                   Prefix        Direction
----------------------  ------------  ------------------------
ViewCommands            emitXxx()     Model → notifies Controller, creates Event
ViewEventHandlers       onXxx()       Controller → processes Event, call ViewInterface
ViewInterface           showXxx()     Notifies View (Console or GUI)
CrapsCommands           cmdXxx()      UI → Controller (commands, createsEvent)
CrapsEventHandlers      onXxx()       Controller → processes Event, executes model command
CrapsReaders            readXxx()     UI → Controller (queries model directly read-only info)



pub/sub event for UI menus and friends
--------------------------------------

class UIEventBus {
public:
    using Handler = std::function<void(const GameEvent&)>;
    using SubscriptionId = size_t;

    static UIEventBus& instance() {
        static UIEventBus bus;
        return bus;
    }

    // subscribe: returns a token you can use to unsubscribe
    SubscriptionId subscribe(EventType type, Handler handler) {
        auto id = nextId_++;
        subscribers_[type].emplace_back(id, std::move(handler));
        return id;
    }

    void unsubscribe(EventType type, SubscriptionId id) {
        auto& vec = subscribers_[type];
        vec.erase(
            std::remove_if(vec.begin(), vec.end(),
                [id](auto& pair) { return pair.first == id; }),
            vec.end()
        );
    }

    void publish(const GameEvent& ev) {
        auto it = subscribers_.find(ev.type());
        if (it != subscribers_.end()) {
            for (auto& [id, handler] : it->second) {
                handler(ev);
            }
        }
    }

private:
    size_t nextId_{0};
    std::unordered_map<EventType,
        std::vector<std::pair<SubscriptionId, Handler>>> subscribers_;
};


Menus use it like this:

class MenuBetting {
public:
    void onActivate() {
        subId_ = UIEventBus::instance().subscribe(
            EventType::ViewErrorDialog,
            [this](const GameEvent& ev) {
                if (ev.correlationId == myCorrelationId_) {
                    showError(ev.message);
                }
            }
        );
    }

    void onDeactivate() {
        UIEventBus::instance().unsubscribe(EventType::ViewErrorDialog, subId_);
    }

private:
    UIEventBus::SubscriptionId subId_{0};
};
