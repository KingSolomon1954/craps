Detailed Description

Managers players.

Manages players.

Maintains a central index file (e.g., players/index.json) listing all known player IDs and names for fast access/UI.

PlayerManager Responsibilities:

  • Maintain list of player IDs
  • Own each loaded player's file (YamlFile) and controller-level preferences (PlayerPrefs), and decide when they are read and written
  • Create new player
  • Know who the user player is, and switch it
Player files

Craps::Player knows nothing about files. It only converts itself to and from YAML. PlayerManager owns the rest:

  • The starting players are read once at startup, each from the "Player" section of its file and the "Prefs" section for PlayerPrefs.
  • shutdown() takes a fresh snapshot of every Player and every PlayerPrefs and writes each file. Failures are logged with LOG_ERROR; one player failing does not stop the others. Call it once at quit, and only after TableManager::shutdown(). The table is what shuts the players down, and Player::shutdown() is what merges the session into the stats. Saving before that would write the stats without this session. Player::shutdown() is not repeatable, so PlayerManager does not call it again itself.
  • userPrefs() is the preferences of whoever is the user player right now. getPrefs() is the same for any player, by id.
The user player

The user player is the player the person at the keyboard is playing as. It is one of the starting players until switchPlayer() makes someone else the user. switchPlayer() never leaves things half done: if it fails, the current user player is still at the table, still the user, and can keep playing. It catches everything, so it never throws.

switchPlayer(toPlayerId):

  • toPlayerId must be a known player (the manifest), must not be the current user, and must not already be at the table. A player who is not loaded yet is read from his file first. Any of these failing changes nothing.
  • The table swaps the two players (CrapsTable::replacePlayer()). The user player's session ends, his bets are taken off the table and returned to him, and the new user takes his seat, and the dice if he had them. The View is expected to confirm with the person first if there are bets on the table.
  • Then the player who left is written to his file. If that write fails it is logged; the switch still stands.

A player who switched out stays loaded. If he is switched in again later he starts a new session.

Threads

Requests arrive on the EventManager thread while the View thread reads through CrapsReaders. The manager's own bookkeeping (who is loaded, who is the user) is guarded by a mutex. getPlayers() hands out a reference and so is not protected; do not call it while a switch can be running.
