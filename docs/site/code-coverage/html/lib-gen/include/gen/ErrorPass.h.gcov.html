     171             : @brief A generic error payload for value-based error handling.
     172             : 
     173             : There are two basic ways to use ErrorPass:
     174             : 
     175             : 1. Value-based - using std::expected (or zeus::expected)
     176             : 
     177             : 2. Call-chain - using in/out function parameter
     178             : 
     179             : Value-based ErrorPassing
     180             : ------------------------
     181             : 
     182             : Error passing combined with `zeus::expected` provides a type-safe,
     183             : value-based error handling scheme. Instead of throwing exceptions or using
     184             : primitive return status codes, functions return a `zeus::expected<T, ErrorPass>`.
     185             : 
     186             : If a function succeeds, it contains its value of type `T`. If it fails, it
     187             : carries an `ErrorPass` payload containing metadata about the failure and
     188             : the location where it occurred.
     189             : 
     190             : Call-chain ErrorPassing
     191             : -----------------------
     192             : 
     193             : With call chain error passing, an ErrorPass object is declared at the
     194             : top of a call chain and then supplied directly in the signature of
     195             : functions that have coded for it. The caller supplies the ErrorPass
     196             : object which will be filled out by the callee when an error is
     197             : encountered and left untouched if there is no error.
     198             : 
     199             : The callee then in turn uses the error passing object it was given
     200             : and passes that along to child functions it calls, forming a chain of
     201             : calls using the same error passing object from the top. This strategy
     202             : requires writing functions with a signature accepting an error
     203             : passing object up and down the call chain. This sounds yucky at first
     204             : but becomes second nature in practice and profoundly useful.
     205             : 
     206             : Extensible with application domain error names and types.
     207             : ---------------------------------------------------------
     208             : 
     209             : The standard ErrorName and ErrorType enums provide names for common
     210             : library errors. Applications may also supply their own error names and
     211             : types as strings; no derived error class or enum extension is
     212             : required. Error names and types are stored as strings. An empty error
     213             : name means that no error is set. Severity remains a standard enum.
     214             : 
     215             : Example using the standard vocabulary:
     216             : 
     217             : @code
     218             : ErrorPass ep;
     219             : EP_SET(ep, ErrorPass::ErrorName::NetworkError,
     220             :        ErrorPass::ErrorType::CommunicationsError,
     221             :        ErrorPass::Severity::Critical,
     222             :        "Failed socket write");
     223             : @endcode
     224             : 
     225             : Example using application-defined vocabulary:

     227             : @code
     228             : ErrorPass ep;
