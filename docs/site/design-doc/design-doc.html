Design of Royal Craps

This document describes the design of Royal Craps version 0.1.0.

Royal Craps is a craps game for the Linux terminal. It plays the way a casino table does, with the full layout, the real payouts and the house commission, and you can play it alone or with computer buddy players at the table. It offers these features:

  • Line, Odds, Come, Place, Buy, Lay, Field, Hardway, and Proposition Bets

  • Choice of tables: Las Vegas Strip and High Roller

  • Automatic Odds

  • Quick Bets

  • Bet Flags: keep bets up, take them down, or work them on the next roll

  • Undo

  • Play with Up to Five Computer Buddies

  • Several players, each with a bankroll and history of their own

  • On-Screen Dice Roll Animation

  • Dice Roll history

  • Dice Stats

  • Player Stats Current Session

  • Player Stats Across All Sessions

  • Table Stats Current Session

  • Table Stats All Sessions

  • Terminal Based UI (future GUI)

This document is primarily for developers maintaining the application itself, however, other interested developers and engineers may find it useful.

Introduction

User Story

As a person who likes craps, but not the risk of losing real money, I want to sit at a casino style craps table on my own Linux computer and play it the way it is played in a casino.

As a user of Royal Craps, I want to:

  • Place any of the bets found on a casino table: Pass Line, Don’t Pass, Come, Don’t Come, Place, Buy, Lay, Field, Hardway and the proposition bets, with odds behind the line bets, and have the table pay them by the real rules.

  • Learn the game without risking a dollar, because the table shows the limits for a bet and tells me why when it refuses one.

  • Try a betting system and see how it does over many rolls, with statistics for me, for the table and for the dice.

  • Save time on the bets I make over and over, with Quick Bets, Automatic Odds and Bet Flags, and take back a mistake with Undo while betting is open.

  • Share the table with buddy players, and have several players of my own, each with a bankroll and a history that are there the next time I play.

  • Choose a table with limits and odds that suit my bankroll.

  • Play from the keyboard in a terminal, with the dice animated and a history of the rolls in view.

Design Goals

The important design goals and constraints are these.

  • Casino rules, as data. The rules of a table (limits, odds allowed, payouts and commission) are data in the table’s file, not code, so a table with different rules is a new file. See The Rules Are Data.

  • An engine that does not know the screen. The Craps Engine knows nothing of the View, so a graphical interface can be added beside the console interface and use the same engine and Controller. See MVC and the Libraries.

  • A screen that is never held up. The console interface runs on its own thread, and a request from the screen is answered by an event instead of a call that waits. See Threads and Processing Flow.

  • Refuse, explain and change nothing. A bet or other request that is not allowed is refused whole, with a reason the person can read, and leaves the game as it was.

  • Persistent and simple. Players and tables are kept in YAML files that a person can read. There is no database and no network. See Persistence and Configuration.

  • Testable in pieces. The engine and the Controller run without a screen, and unit tests play whole rolls and whole sessions.

  • Single process, built for Linux. The language is C++20 and the console interface uses ncurses.

  • Documentation built with the code, so that it stays true to it.

Architecture

Application Context

The Royal Craps design is a single process application with multiple threads written specifically for Linux. C++ is the language choice.

There is no database, just a bunch of persistent files. The application performs no networking.

MVC and the Libraries

The design conforms the Model/View/Controller design paradigm. There is the CUI and GUI making up the View, the Controller, and the Craps Engine making up the Model. Implementation-wise, we have:

  • Model - lib-craps

  • View - lib-cui / lib-gui

  • Controller - lib-controller

  • General purpose library - lib-gen

Threads and Processing Flow

Thread Inventory

Royal Craps is one process with four threads, plus the signal handling done by the main thread. Each thread has a single job.

Thread

Started by

What it does

Main

The operating system

GameMain builds the application in its constructor, then blocks in SignalHandler::waitForTerminate() until a termination signal arrives or the user quits. It then runs the shutdown.

Event

Gen::EventManager, the first time it is used

Takes each published event off the queue and runs its handlers, one event at a time. All the work of the Controller and the Craps Engine that responds to the View happens here: handling requests, placing and resolving bets, rolling the dice, saving files.

CUI

Cui::CuiThread, when the Console UI starts

Owns the screen. It reads the keyboard, runs the work queue (keys, events from the engine, drawing requests), and draws. Only this thread uses ncurses and the View’s windows and menus.

Timer

Gen::TimerManager

Runs every timer from one thread. The only timer user today is the dice animation. Its callback does no drawing. It places a draw request on the CUI thread’s work queue.

The main thread installs SignalHandler first, before any other thread exists, so that every thread inherits a mask that blocks the signals. Only the main thread waits for them.

Thread Rules

  1. Only the CUI thread touches the screen. Anything that wants something drawn, from any thread, queues a work order for the CUI thread.

  2. Events are the way across threads. The View sends requests with CuiSender, which publishes onto the event queue. The engine and Controller answer by publishing, and CuiReceiver turns what the View subscribed to into work orders for the CUI thread. See Events.

  3. The Controller and the Craps Engine are not thread safe in themselves. They get away with it because nearly all of their work runs on the single event thread, and the event thread runs one handler at a time. A handler can therefore assume nothing else is changing the engine while it runs. PlayerManager also has a mutex of its own.

  4. The View may read the model without going through events. It does this through CrapsReaders, from the CUI thread, while the event thread may be changing the model. These readers take no locks. The design relies on these habits to make that safe enough:

    • The View only reads. It never changes the model except by sending a request.

    • Displays that need consistent numbers keep a cache, updated by events, instead of reading the engine on every draw.

    • An object the View might be reading is not deleted while the game runs. For example, when the game switches tables, the old table is retired and kept until the game ends.

  5. A handler does not wait. Handlers on the event thread must finish quickly, and must not block on the CUI thread, because every other event waits behind them.

Shutdown and the Threads

Quitting from the game sends ReqTerminate. Its handler asks GameMain to release the main thread, as a signal does. The main thread then shuts down in this order:

  1. The View stops first, which stops the CUI thread and gives the terminal back. Nothing is reading the model after this. Events published later are dropped by the View.

  2. The table shuts its players down and saves itself.

  3. PlayerManager saves the players, and the user state is saved.

  4. The event and timer threads end when their singletons are destroyed as the process exits. The event queue is emptied first.

Processing Flow of a Bet

A bet shows the pattern that most user actions follow.

CUI thread                      Event thread
----------                      ------------
key pressed
menu, dialogs, OperationManager
CuiSender::reqMakeBet()  ---->  queue --> EventHandler::onReqMakeBet
                                          CrapsTable adds the bet
                                          publishes UslBetMade, ...
                         <----  queue <-- publishes RspMakeBet
CuiReceiver: work order
WorkOrderDispatcher

windows redraw from the events

The View does not wait for the answer. OperationManager remembers the operation in progress and finishes it when the response arrives, matching it by correlation id. The next key is handled in the meantime.

Processing Flow of a Roll

Rolling the dice follows the same path, but the engine does the whole roll in a single call on the event thread. ReqRollDice clears the undo history, since the bets are about to be decided, and then calls the table’s rollDice(). That call publishes the events for the roll, in order, from betting closed to betting opened. There is no response event. The results come back as the unsolicited events. The CUI holds them until the dice have landed. See Roll Animation Synchronization.

Events

Why Events

The Model, Controller and View do not call each other’s code to make things happen. A layer that wants something done publishes an event, and a layer that wants to know what happened subscribes to the events it cares about. The layers share only the event definitions. A graphical View can therefore take the place of the console one without changes to the engine, and the engine can be tested without a View.

The View also reads state directly, through CrapsReaders, for example the table name or a player’s balance. Events carry changes. Readers answer questions about how things are now. See Thread Rules.

The Event Bus

Gen::EventManager is the event bus, a thread safe publish and subscribe queue.

  • Events are plain structs. A subscriber names the struct type it wants, and gets only that type.

  • publish() copies the event onto a queue and returns at once. It never runs handlers itself.

  • One worker thread, the event thread, takes events off the queue in the order they were published and calls each subscriber, one after another.

  • A handler that publishes new events adds them to the back of the queue. They are delivered after every event already waiting.

  • A handler that throws does not stop the bus. The exception is dropped. Handlers should catch and report their own errors.

  • Subscriptions last as long as the process. There is no unsubscribe.

Event Categories

Every event is a struct derived from GameEvent and is one of three kinds, named by prefix. The full list is Ctrl::EventType in GameEvents.h.

Prefix

Direction

Meaning

Req

View to Controller

Please do something. Examples: ReqRollDice, ReqMakeBet, ReqUndoBet, ReqSwitchTable, ReqTerminate.

Rsp

Controller to View

The answer to one request, carrying success or an error. Examples: RspMakeBet, RspSwitchTable, RspApplyQuickBets.

Usl

Any layer to whoever listens

Unsolicited. Something happened. Examples: UslBettingOpened, UslDiceNewValue, UslBetResolved, UslTableSwitched.

Not every request has a response. A request whose outcome is shown by the unsolicited events that follow it, such as ReqRollDice, has none, and neither does a request that cannot fail, such as ReqSetAnimationSpeed.

The unsolicited events fall into groups:

  • The roll. Betting closed, dice thrown, dice value, bets resolved start and end, point established, seven out, pass line winner, new shooter, betting opened.

  • Bets. Bet made, removed, changed, resolved, or failed evaluation.

  • State for displays. Table and player bets, session stats, last roll stats and balances. These let a display keep a cache without polling.

  • Roster and settings. Player joined or left the table, user player switched, player renamed, table switched, roll history format changed.

  • Automation. AutoOdds applied.

Event Sources and Correlation

Each event records where it came from (EventSource: Model, View or Controller) and carries two numbers:

  • A unique event id.

  • A correlation id. A new event starts with its own unique value. The handler that answers a request copies the request’s correlation id into the response. The sender uses it to tell which of its requests a response answers.

Delivery Order

The order guarantees are simple, and the design depends on them:

  1. Events are delivered in the order they were published, to every subscriber of their type.

  2. One handler runs to completion before the next event is delivered.

  3. A response is therefore always delivered after anything the handler published before it.

  4. The CUI thread’s work queue is also first in, first out. The View sees events in the order the engine published them. CuiReceiver does not reorder, and the View can choose to hold some back. See Roll Animation Synchronization.

Adding an Event

A new event touches these places:

  1. GameEvents.h: the struct and an EventType value.

  2. The publisher, and for a request the EventHandler subscription and handler.

  3. For the View: WorkOrder.h (the variant), CuiReceiver (the subscription and handler), WorkOrderDispatcher (process(), and the pass-through list if it is a response), and CuiSender if it is a request.

Roll Animation Synchronization

Roll Animation Purpose

The Craps Engine resolves a dice roll in a single synchronous burst: it picks the dice, evaluates every bet, updates balances and statistics, and publishes the resulting events, all within one call. The CUI, on the other hand, shows the dice tumbling on screen for a second or two. If the CUI simply handled each event as it arrived, bets would be cleared and balances would change while the dice were still in the air, and the player would see the outcome before the roll is known.

The CUI therefore holds back the results of a roll until the animation shows the dice landing, then reveals all of them together. The Craps Engine and the Controller know nothing about this. The synchronization lives entirely in the CUI.

Participants

  • CuiReceiver subscribes to the engine’s events and converts each into a work order placed on the CuiThread queue, in the order the engine published them.

  • CuiThread processes the queue on the CUI thread and hands every work order to WorkOrderDispatcher. Its loop also gives the dispatcher a regular tick().

  • WorkOrderDispatcher decides whether an event is handled now or held, and replays held events when released.

  • WindowAnimation renders the dice frames from a timer. It alone knows when the dice have landed.

Event Ordering

For one roll the engine publishes, in this order:

  1. UslBettingClosed

  2. UslDiceThrowStart

  3. UslDiceNewValue

  4. The results: bets resolved, bets removed or changed, balances, session and last-roll statistics, point established, seven out, new shooter, and UslResolveBetsEnd

  5. UslBettingOpened

Because the queue is first-in first-out, UslDiceThrowStart is always handled before any of the results.

Holding and Releasing

Engine            CuiThread / Dispatcher           WindowAnimation
------            ----------------------           ---------------
ThrowStart  --->  onDiceThrowStart()  ---------->  start frame timer
                  holding = true                   (frame every ~90 ms)
NewValue    --->  dice to animation (now)
                  roll history, title bar (held)
results     --->  queued, in order (held)
                                                   ... frames ...
                                                   dice land
                  <-- ReleaseHeldEvents work order
                  replay held events in order
                  holding = false, one full redraw

While holding:

  • Held are the results of the roll: all bet, balance and statistics events, point and seven-out events, shooter changes, roster changes, and the roll history and title bar portions of UslDiceNewValue.

  • Not held are UslDiceThrowStart, the animation’s own portion of UslDiceNewValue (it must have the dice to draw them), UslBettingClosed, and every Rsp response event. Responses answer requests the player made and must reach OperationManager without delay.

Held events are stored as closures and replayed in their original order, so each panel sees the same sequence of calls it would have seen without holding. Panels need no knowledge of the mechanism. In particular, panels that re-read the model after a roll, such as the player area when it handles UslResolveBetsEnd, do so at release time and therefore never show post-roll data early.

When WindowAnimation draws its final frame it enqueues a ReleaseHeldEvents work order rather than calling the dispatcher directly. The release is then handled like any other work order, in sequence, on the CUI thread, so no locking is needed.

Rules

  • The animation always plays out. A key press does not skip or shorten it.

  • Safety net. If the animation never reports that the dice landed, the dispatcher’s tick() releases the held events after MaxHold (ten seconds) and logs a warning, so the screen cannot stay frozen.

  • No animation, no hold. WindowAnimation::onDiceThrowStart() returns whether the dice will be animated. If it returns false, nothing is held. The dice show immediately and results are handled as they arrive.

Animation Speed

The Animation Speed option on the Control, Configuration menu drives this mechanism through two small functions in WindowAnimation. Both read the setting from CrapsReaders::readAnimationSpeed() at each throw, so a change applies to the next roll:

  • animationEnabled() is false for Off, so there is no animation and no hold. onDiceThrowStart() returns false and the dispatcher passes the roll’s results straight through.

  • frameInterval() sets the timer period: 45 ms for Fast, 90 ms for Normal and 135 ms for Slow. The length of the animation scales with it.

Slow is about two seconds, well under MaxHold. If an animation can ever become much slower than that, MaxHold must be raised to stay above the longest animation.

The setting lives in the configuration as animation.speed. The session layer, the highest priority, holds a choice made in the menu, which sends ReqSetAnimationSpeed. Below it are the command line (--animation-speed), config.yaml, and what state.yaml remembered. At quit the session choice, or else the remembered value, is written back to state.yaml under settings. A config.yaml value is never written there, so removing it from config.yaml restores the remembered speed.

Game State

The state of the game lives in the Craps Engine, in CrapsTable. A table is always in one of these states:

Come-out roll  ---- 4,5,6,8,9,10 ------>  Point on
     ^   |                                  |   |
     |   +-- 2,3,7,11,12: stays            |   |
     |                                      |   |
     +-------- point made (pass line wins) -+   |
     +-------- seven out (next shooter) --------+

  • Come-out roll (no point). A roll of 4, 5, 6, 8, 9 or 10 sets the point and publishes UslPointEstablished. Any other number leaves the table in the come-out state.

  • Point on. A roll equal to the point publishes UslPassLineWinner. A 7 publishes UslSevenOut and passes the dice to the next shooter. Either ends the point, and the table goes back to the come-out roll.

Independently of that, betting is open or closed. Betting is open except for the length of a roll. UslBettingClosed and UslBettingOpened bracket every roll. The Controller refuses requests that change bets while betting is closed, and refuses a table switch.

Only the engine changes this state, and only when it handles a request or a roll. Everything else in the application learns of it from events.

View State

The View keeps its own state, none of which the engine knows of:

  • The screen. SurfaceManager holds the stack of what is on the screen. The table screen is at the bottom and the menus and dialogs stack above it. Keys go to the top surface.

  • The operation in progress. OperationManager tracks at most one multi-stage user operation, and the stage it has reached. See OperationManager CRC Card.

  • Held events. WorkOrderDispatcher may be holding events while the dice are rolling. See Roll Animation Synchronization.

  • Display caches. Windows keep the numbers they show, such as the house figures and the roll list, and update them from events.

Between them these cover everything the user sees. When the game changes tables, the Controller sends UslTableSwitched and then a snapshot of the new table’s state, and the View resets its caches from them.

The Application’s Own State

The process itself is in one of three states, owned by GameMain:

  1. Starting. The constructor creates the globals, then the View. See Startup, Shutdown and Directory Layout.

  2. Running. The main thread waits for a termination signal or for ReqTerminate.

  3. Stopping. explicitShutdown() stops the View, then saves the table, the players and the user state. See Thread Inventory.

A failure while starting, such as an invalid configuration, ends the process with a message and a non-zero exit status. A failure once the game is running is reported and logged, and play goes on. See Error Handling.

Startup, Shutdown and Directory Layout

Startup Behavior

Royal Craps must bring the user straight into a working game, with no configuration steps, on a fresh installation and on every start after. Packaged files are read-only and shared, so everything the game writes (players, tables, preferences, what was last played) lives in the user’s own directories and is created from the packaged defaults when missing.

The configuration is resolved in layers, each overriding the one before: built-in defaults, the files (packaged sys-config.yaml, then the user’s config.yaml), environment variables, and finally the command line. The directories themselves can be overridden with --sys-config-dir, --usr-config-dir, --usr-data-dir and --usr-state-dir. Pointing the user directories at a scratch location gives a genuine first startup every time, which is how first startup is tested; pointing them at the packaged files is how development runs from a source tree.

Logging During Startup

The log file is in the user state directory, which is not known until configuration is resolved, yet startup itself needs to log. The logger therefore holds messages in memory (and still echoes them to the console) until it is given its file, then writes them to the file ahead of everything else with their original timestamps. If startup fails before then, the held messages have already appeared on the console. Debug and trace messages are only kept once those levels are known, so the earliest messages are informational, warnings and errors.

First Startup

First startup is detected by the absence of the user’s config.yaml. The same population work also runs if the user’s players.yaml or tables.yaml is missing, so a user who deletes their data directory gets a working game back rather than an error.

Royal Craps performs the following steps:

  1. Creates the user directories.

  2. Copies the packaged files into the user directories. A file is copied only if it does not already exist there, so existing players and their statistics are never overwritten. Each file is copied to a temporary name and renamed into place. These include:

    • player unnamed.yaml.

    • packaged buddy player YAML files.

    • packaged table YAML files.

    • the players.yaml and tables.yaml manifests.

  3. Copies default-config.yaml to the user’s config.yaml. This is done last, so an interrupted first startup is simply repeated on the next start.

  4. The delivered config.yaml says nothing about the table or players, so the packaged defaults in sys-config.yaml apply: table las-vegas-strip.yaml, user player unnamed.yaml and two buddy players.

  5. The delivered unnamed.yaml specifies a starting bank of $10,000.

  6. Royal Craps continues start up as normal.

  7. Game begins with full screen ScreenCrapsTable.

  8. If the user player’s name is unnamed then a message reminds the user to change the name. Until the main screen has a message area this is an acknowledged dialog.

Subsequent Startups

  1. Reads config.yaml from the user’s config directory.

  2. Reads state.yaml from the user’s state directory, if there is one.

  3. Decides the table and players as described in Choosing the Table and Players.

  4. Loads the user player, the table and the other players from the user’s data directory.

  5. Game begins with full screen ScreenCrapsTable.

  6. If the user player’s name is unnamed then the same reminder is shown.

At quit, after the table and players are saved, the table, the user player and the other players seated at the table are written to state.yaml.

Choosing the Table and Players

Three sources can say which table and players to start with, in this order of authority: what the user wrote in config.yaml, what the last game left in state.yaml, and the packaged defaults in sys-config.yaml. The user’s config.yaml always wins; state.yaml only fills in what it leaves out. Each setting is decided on its own.

config.yaml setting

Meaning

startWithTable

Always start at this table. If absent, the last table, else the packaged default.

startWithUserPlayer

Always start as this player, whoever the user played last time. If absent, the last user player, else the packaged default.

startWithBuddyPlayers

true (the default) or false. false means start with no buddy players, regardless of anything else, including the buddies of the last game.

startWithTheseBuddyPlayers

A list of up to five buddy players to always start with. If absent, the buddies of the last game, else the packaged default buddies. Ignored when startWithBuddyPlayers is false.

The packaged defaults are defaultTable, defaultUserPlayer and defaultBuddyPlayers in sys-config.yaml. They are separate keys because a value present in sys-config.yaml under the names the user uses could not be told apart from something the user wrote. A game that was left with no buddies is remembered as having none; the default buddies are only for when there is no state.yaml.

The game must always be able to start, so a file name that does not exist in the user’s tables or players directory (a typing mistake, or a player that was deleted) is skipped with a warning in the log and the next source is tried; for buddies, just that one buddy is dropped. The user player is never also a buddy. A state.yaml that cannot be read is ignored, and deleting it is always safe.

The result is stored under the keys the rest of the game reads: table.startTable, table.userIsPlayer and table.startPlayers.

Packaged files added by a later release (a new table or buddy) are not copied into an existing installation, and are not in the user’s manifests. A way to deliver them is not yet defined.

Reading and Writing

All of these files are handled by YamlFile, which holds a file as a document of named sections:

  • The model classes see only their own section, as a YAML node. They know how to convert to and from it, and nothing about files. CrapsTable reads and writes the Table section, Player the Player section, PlayerPrefs the Prefs section.

  • The managers own the YamlFile objects, and decide which sections a file has and when to read and write it.

  • A section the game does not know of is kept and written back, so something added by hand or by a later version survives.

  • save() writes to a temporary file in the same directory and renames it over the real file. A failed or interrupted write leaves the old file intact.

  • Loading is forgiving where it can be. An entry in a preferences section that cannot be read is logged and skipped. The one required section of a file must be present, or the file fails to load.

When Files Are Written

Files are written at particular moments, not after every change:

  • At quit, the table, every player, and state.yaml.

  • When the user player changes, the player who left.

  • When a player leaves the table, that player.

  • When the table changes, the old table, and every player.

  • When a player is created, that player and the manifest.

  • When a player is renamed, the manifest at once. The player’s own file is written with the next of these.

  • When the buddy follow setting changes, the players.

Changes to preferences such as QuickBets or AutoOdds are written with the next of these. A game that ends without a normal quit, such as a crash or a kill signal, loses what has changed since the last of them. A failure to save is logged, and does not stop the game or the other saves.

Order matters at quit. The table first ends each player’s session, which merges it into the player’s statistics, and saves itself. Only after that are the players saved. See Shutdown and the Threads.

Configuration Layers

Settings that are not saved by the game, but supplied to it, come from ConfigManager, built on Gen::MultiLayerConfig. A setting is a string keyed by a dotted name, such as animation.speed. The layers, each overriding the one before, are:

  1. Built-in defaults.

  2. Files: the packaged sys-config.yaml, then the user’s config.yaml.

  3. Environment variables.

  4. The command line.

  5. A session layer, the highest, holding settings the game itself changes while it runs, such as the animation speed chosen from the Configure menu.

A value is looked up by key and the highest layer that has it wins. It is read as a string, an integer or a boolean. The key names are constants in ConfigManager. The directory settings can be changed from the command line, which is how a development run uses the source tree, and a test run uses a scratch directory.

What the last run remembered, in state.yaml, is used only when the user’s config.yaml does not say. For example, the animation speed in config.yaml wins, and otherwise the speed from the last game is used. The same rule applies to the roll history format.

StartChoices turns these settings and the remembered state into the table and players the game starts with. See Choosing the Table and Players.

Error Handling, Logging and Timers

Error Handling

Errors are reported in three ways, depending on where they happen.

Error passing. Most of the engine and the Controller report an expected failure, such as a bet that the table does not allow, with Gen::ErrorPass. An ErrorPass holds an error name and type, a severity, a description, and where the error arose. There are two forms:

  • Value-based. A function returns zeus::expected<T, ErrorPass>, which holds the value or the error. The engine uses this, for example in Player::makeOrChangeBet() and Player::joinTable().

  • Call-chain. The caller passes in an ErrorPass that the function fills in on failure, and the function returns a ReturnCode. The Controller’s managers use this.

A function that passes an error up the call chain adds its own context with EP_TRACE, so the error carries the path it took. The names and types are strings, so the application can use its own as well as the standard ones.

Exceptions. Code that cannot continue throws, and in particular code that reads files. YamlFile throws on a file that cannot be read or written. The managers catch these, log them, and turn them into an ErrorPass or carry on, as the case calls for. A handler running on the event thread must not let one escape. The bus drops it. See The Event Bus. Exceptions during startup are not caught until main(), which prints the message and ends the program.

Logging. A failure the user does not need to hear about is only logged.

How an Error Reaches the User

An error from a request goes back to the View in the response event, which carries the ErrorPass. OperationManager ends the operation and shows the error in a dialog that says what failed and why. The operation is finished when the user dismisses the dialog. A success may show a notice. The View never sees an exception from the Controller, because requests cross the event bus.

Logging

Gen::Logger is a singleton, usable from any thread. There are five levels: debug, trace, info, warn and error. Each log line has a timestamp and a level.

  • Messages go to the log file in the user state directory, and until the screen takes over, also to the console. GameMain turns console output off before the View starts, since the console belongs to ncurses.

  • Before the file is known, messages are held and written to it first, when it is set. See Logging During Startup.

  • Debug and trace messages are compiled in only in a debug build. A debug build writes them only when the log.debug and log.trace settings are on. Informational, warning and error messages are always kept.

  • The macros LOG_TRACE, LOG_DEBUG, LOG_INFO, LOG_WARN and LOG_ERROR are used in the code. Each entry into a handler logs a trace message with the name of the function.

Timers

Gen::TimerManager runs any number of one-shot or repeating timers on a single thread. A timer is created with a callback, armed, and cancelled or restarted by its id.

A timer callback runs on the timer thread, so it must be short, and it must not touch anything that belongs to another thread. The dice animation shows the rule. Its callback only queues a draw request for the CUI thread, and the drawing is done there. See Thread Inventory.

Memory Management and Security

Memory Management

Ownership is held by one object, and the rest only point to it.

  • GameMain creates and owns the globals, and releases them in reverse order when it ends.

  • TableManager owns every CrapsTable, with the file each was read from. A table the game has left is retired, not deleted. See Table Switch Steps.

  • PlayerManager owns every Player along with its preferences and its file. A CrapsTable only points to the players seated at it, and a Player only points to the table it sits at. Neither owns the other.

  • The View owns its windows, menus and dialogs. The Controller and the engine do not point into the View.

  • Events are copied into the bus. An event is not shared between publisher and subscriber.

Smart pointers (std::unique_ptr) are used for ownership. Raw pointers mean “not owned”. The design makes no use of reference counting.

The program uses little memory, since there is a handful of players and tables, and history is capped. A table keeps a limited number of its sessions in its history, set by the table.maxSessions setting.

Security

Royal Craps runs as an ordinary user and has no network access. It reads and writes files only in the user’s own directories and in its temporary files beside them. It holds no credentials, accounts or real money. The user can edit the files in the user’s directories, so the game reads them without trusting them. A file that cannot be read is reported, or an unusable entry is skipped, and the game still starts. The dice use a standard random number generator, which is right for a game and not meant for anything that needs unpredictable numbers.

Model

Model Overview

The Model is the Craps Engine, in lib-craps. It knows how a craps table works: who is at the table, what bets are on it, what a roll does to each bet, who gets paid, and what the statistics say. It knows nothing of the screen, and nothing of files.

  • It never calls the View or the Controller. It reports what happens by publishing unsolicited events. See Events.

  • It does not read or write files. The classes that have a saved state convert themselves to and from YAML nodes, and the Controller decides where the YAML is kept. See Persistence and Configuration.

  • It does not read the configuration. What it needs is given to it when it is built, in a TableConfig and in the table’s rules.

  • It is tested on its own, with unit tests that play whole rolls.

The Rules Are Data

How a table pays, and what it allows, is not written into the code of the bets. It is a value, TableRules, read from the table’s file. It holds the limits for each bet, the odds the table allows, the payouts, whether there is a commission and how it is collected, and how payouts are rounded. This is how the Las Vegas Strip and the High Roller table are the same code with different files. A bet is evaluated against the rules of the table it is on.

How a Roll Is Resolved

CrapsTable::rollDice() does a whole roll in one call, in this order:

  1. Betting closes, and the players are told.

  2. The dice are thrown. The table keeps the recent rolls and counts the roll in its statistics.

  3. Every bet on the table is evaluated, one at a time, against the point, the dice and the rules. Each answers with a DecisionRecord: won, lost, no decision, how much, and whether the bet comes down. If any evaluation fails, no decision is applied and the table is left as it was.

  4. The decisions are carried out. Winners are paid by the house, and losing money goes to the house. The house bank is refilled if it runs low. Bets that are finished come off the table, and each player is told.

  5. The table moves to its next state: the point is set or ended, and the dice go to the next shooter after a seven out.

  6. Betting opens.

Events are published at each step, as listed in Roll Animation Synchronization.

CrapsTable CRC Card

One table, and everything that happens at it.

Responsibilities

  • Seat the players and know who is shooting. Pass the dice to the next shooter after a seven out.

  • Accept or refuse bets against the table’s rules and limits, and keep every bet on the table.

  • Run a roll: throw the dice, have each bet decide, pay the winners and collect from the losers, and take finished bets off the table.

  • Keep the table’s state: the point, the shooter, whether betting is open, and the recent rolls.

  • Keep statistics for the current session and for all sessions, and close a session when the table is left.

  • Convert itself to and from YAML.

  • Publish events for all of the above.

Player CRC Card

One player, their money and their bets.

Responsibilities

  • Hold the player’s money in a bank, with its statistics.

  • Make, change and remove the player’s bets. A player has at most one bet for each spot, as at a real table. Making a bet that already exists changes its amount.

  • Join and leave a table.

  • Receive the results of a roll, adding wins to the balance and recording the statistics.

  • End a session by taking the bets down, returning the money, merging the statistics and recording the session. The player can then join a table again and start a fresh session with the same balance.

CrapsBet CRC Card

One bet on one spot.

Responsibilities

  • Know what it is: its name, its amount, its pivot (the number it is on, such as the 8 for a place bet), the odds on it, and when it was made.

  • Evaluate itself for a roll, against the point, the dice and the table’s rules, and answer with a DecisionRecord.

  • Know its flags: whether it is working or off, and for one roll or until changed. See Bet Flags.

  • Know whether it is live for a roll, which depends on the point and on its flags.

  • Refuse to be made wrong, by checking that its name, amount and pivot agree with each other.

Only CrapsTable and Player change a bet’s amounts. Everyone else reads them.

How a Key Becomes an Action

  1. CuiThread reads a key and places a work order for it on its own queue.

  2. WorkOrderDispatcher gives it to SurfaceManager, which passes it to the top surface.

  3. A menu acts on the key. It may open another menu, or start an operation in OperationManager.

  4. When the operation has what it needs, OperationManager calls CuiSender, which publishes the request.

How an Event Becomes a Display

  1. CuiReceiver, on the event thread, receives the event and places a work order for it on the CuiThread queue.

  2. WorkOrderDispatcher, on the CUI thread, either holds it, if the dice are rolling, or passes it on. See Roll Animation Synchronization.

  3. The dispatcher calls the panels and managers that care, with plain values taken from the event, and then asks SurfaceManager to redraw. A response goes to OperationManager.

OperationManager CRC Card

Purpose

OperationManager coordinates the lifecycle of multi-stage user operations in the CUI.

An operation represents a user-initiated task that may involve navigating a chain of menus, obtaining user confirmation, issuing an asynchronous request to the Craps Engine, processing the corresponding response, and presenting any resulting errors.

The manager maintains the state of the active operation and determines what action should occur as the operation progresses through its stages.

Although betting is a primary use case, OperationManager is not specific to betting. It supports any CUI operation that requires coordinated interaction across menus, dialogs, and asynchronous request/response events.

Use Cases

Making a bet

A player navigates through one or more betting menus to configure a bet. When the player has completed the required selections, the CUI issues a ReqMakeBet request event to the Craps Engine.

OperationManager tracks the operation, associates the request with its eventual response, and determines the next action based on the result.

  • Success: The betting menu chain is unwound, returning the player to the appropriate underlying screen.

  • Failure: An error dialog is presented. After the player acknowledges the error, the error dialog is dismissed and the betting menu chain is unwound or otherwise restored according to the intended interaction.

Quitting the game

When the player requests to quit, the CUI presents a DialogConfirmation. The manager associates the confirmation response with the pending quit operation.

  • Confirmed: The manager initiates the quit request by publishing the appropriate asynchronous request event.

  • Cancelled: The operation is abandoned, and the player returns to the preceding interface without issuing the quit request.

Other operations requiring confirmation or multi-stage interaction follow the same general pattern.

Responsibilities

  • Track the active operation. Maintain the identity, type, and current stage of the operation in progress.

  • Coordinate multi-stage workflows. Track progress through menu selection, confirmation, request submission, response processing, error acknowledgement, and completion as applicable.

  • Initiate asynchronous requests. Publish the appropriate request event when the operation reaches the stage at which the request should be issued. For example, publish ReqMakeBet when a bet has been fully configured.

  • Correlate requests and responses. Retain the correlation ID and any necessary operation context so that an incoming response event can be matched to the active request and operation.

  • Process operation results. Determine whether the response indicates success or failure and advance the operation accordingly.

  • Coordinate error handling. On failure, request presentation of the appropriate error dialog, retain the operation context while the dialog is active, and process the player’s acknowledgement.

  • Manage surface-stack transitions. Initiate the appropriate dismissal or unwinding of menus and dialogs when the operation succeeds, is cancelled, or finishes error handling. Leave actual surface-stack manipulation to SurfaceManager.

  • Handle confirmation outcomes. Associate confirmation responses with the operation that requested them and proceed according to the player’s decision.

  • Complete or cancel operations. Release the active operation’s state when its lifecycle has finished, ensuring that subsequent operations can begin.

Collaborators

  • CuiSender: publishes the requests the operations issue

  • WorkOrderDispatcher: delivers the responses and results to it

  • SurfaceManager: pushes, pops and unwinds the menus and dialogs

  • Menus, such as MenuBetting and MenuPlayers: start operations

  • Dialogs, such as DialogPicker, DialogConfirm, DialogBetAmount and DialogError: collect choices and confirmations, and report results

  • CrapsReaders: what it needs to know to offer choices

Operating Constraints

  • One active operation at a time. The CUI may have at most one operation managed by OperationManager in progress. A new operation must not overwrite or interfere with an existing operation.

  • Asynchronous request/response processing. Issuing a request does not imply that the operation has succeeded. The operation remains active until its result has been processed and any required follow-up interaction has completed.

  • Correlation-based response matching. A response must be associated with the request that produced it. Unmatched, stale, or unrelated responses must not advance or complete the active operation.

  • CUI thread ownership. All operation-state transitions and resulting CUI actions must respect the CUI’s thread-ownership rules. Incoming events from other threads must be routed to the CUI thread before they cause UI or operation-state changes.

  • Separation of responsibilities. OperationManager coordinates operations; menus collect choices; dialogs communicate information and collect confirmation or acknowledgement; SurfaceManager manages the surface stack; and the Craps Engine executes game operations and reports their results.

Completion

An operation is complete when its intended outcome has been reached and all required user interaction and CUI cleanup have finished.

Depending on the operation, completion may follow a successful response, cancellation of a confirmation, or acknowledgement of an error.

Once complete, the manager releases the operation’s state and becomes available to coordinate the next operation.

Roll History and Roll Log

Roll Log Purpose

Two parts of the CUI show past rolls: the one-line roll history under the title bar, and the Deep Roll History popup. Both need the same facts about each roll, including whether it was a seven out, a pass line winner or established a point, because those pick the roll’s color. The Craps Engine remembers the dice of recent rolls but not what each roll meant, and those facts arrive as separate events after the roll.

The CUI therefore keeps its own memory of rolls, RollLog, and both displays draw from it.

Roll Log Participants

  • RollLog is a small singleton holding RollEntry values, newest first. An entry has the two dice and three flags: sevenOut, passLineWinner and point. It keeps at most Capacity entries (120) and drops the oldest.

  • WindowRollHistory adds an entry for each new dice value, then marks the newest entry as the seven out, pass line winner and point events arrive. It formats and draws the entries in the format the person chose.

  • DialogDeepRollHistory is a fixed-size popup showing the whole log as 20 rows of 6 columns, newest at the top of the first column, reading down each column in turn. It always uses the most detailed format. It keeps nothing of its own and has no dependency on any menu: whatever offers it calls show().

Roll Log Rules

  • The log is the View’s memory only. It holds what the CUI has seen since it started and is not saved. The engine’s own recent rolls are not used, because they carry no flags.

  • Entries are created and marked by the same work orders as every other roll result. They are therefore held and released with the dice animation (see Dice Roll Animation Synchronization), and the history never shows a roll before the dice have landed.

  • The marks apply to the newest entry only and do nothing when the log is empty.

  • Because the flags are stored per roll, changing the format redraws the entire history with its colors intact. Nothing has to be recomputed.

  • Capacity is the number of cells in the popup. It is a fixed constant, not a user setting. The engine’s TableManager::MaxRecentRolls is kept at the same value.

Roll History Format Setting

The format is a number from 1, the most compact, to 4, the most detailed: 7 8 6, 7,8,6, 7(34) 8(44) 6(33) and 7(3,4) 8(4,4) 6(3,3). It follows the same path as the animation speed. The configuration key is rollHistory.format. A choice made in the Control, Configure menu is sent as ReqSetRollHistoryFormat and stored in the highest priority configuration layer. The Controller answers with UslRollHistoryFormatChanged, and the dispatcher redraws the screen. The answer is needed because the request is handled on another thread, so redrawing when the picker closes could happen before the new format is set. WindowRollHistory reads the setting each time it draws. The choice is remembered in state.yaml at quit unless config.yaml states it.

Betting

Betting Purpose

Betting is the heart of the game. A player puts money on a bet, may change its amount or take it down while betting is open, and has it settled by the roll. This page follows one bet from the person’s keystrokes to the table and back to the screen. The features built on it are Bet Automation, Bet Flags and Undo of Bet Changes.

Betting Vocabulary

Term

Meaning

Bet name

The kind of bet: Pass Line, Come, Don’t Pass, Don’t Come, Place, Lay, Buy, Hardway, Field, Any Craps, Any Seven, Any 7/11, C and E, Horn and World.

Pivot

The number a bet is on. A place bet on the 8 has the pivot 8. A bet with no number has the pivot 0. A Pass Line or Come bet gets its pivot when the point or a come point is set.

Contract amount

The money in the bet itself. The odds amount is kept separately.

Odds

The extra money a Pass Line, Come, Don’t Pass or Don’t Come bet may have behind it once it has a number. The table’s rules set how much.

Betting open

The time between rolls when bets may be made, changed or taken down. Betting closes when the dice are thrown and opens again when the roll has been settled.

Betting Participants

  • MenuBetting and the menus and dialogs behind it (MenuPlaceBet, MenuPivot, MenuOddsBet and DialogBetAmount) gather the bet name, the pivot and the amount. They ask the table, through CrapsReaders, whether the bet is allowed and what the limits are, so the person is told early. They do not decide anything.

  • OperationManager runs the Make Bet, Remove Bet and Odds operations. It sends the request, waits for the matching response and unwinds the menus. See OperationManager CRC Card.

  • EventHandler answers ReqMakeBet, ReqOddsBet and ReqRemoveBet and records an undo step for each change that succeeds.

  • Player makes, changes and removes the bets of one player and moves the money. CrapsTable checks every change against the table’s rules.

  • CrapsBet holds one bet and settles itself when the dice are thrown.

Betting Flow

  1. The person picks a bet in MenuBetting. If the bet needs a number the person picks it in MenuPlaceBet or MenuPivot. The person then enters an amount in DialogBetAmount, which shows the table’s minimum, maximum and increment for that bet. The choices are collected in a CarrierBet.

  2. OperationManager sends ReqMakeBet with the player, bet name, pivot and amount.

  3. EventHandler calls Player::makeOrChangeBet(). A player has one bet for each spot, as at a real table, so asking for a bet the player already has changes that bet’s amount and does not make a second bet.

  4. For a new bet, Player makes the bet and CrapsTable checks it, in this order: betting is open, the player is at the table, the player does not already have it, the amount is not zero, Come and Don’t Pass are allowed at this time, the amount is within the table’s limits, and it is a multiple of the increment. The player’s money is then taken for the bet, plus the commission if the bet pays one up front. If the player does not have the money, the bet is refused. A Pass Line bet made after the point is set takes the point as its pivot.

  5. The bet is on the table. The table and the player publish UslBetMade (or UslBetChanged), UslTableBetsChanged, UslPlayerBetsChanged and UslPlayerBalanceChanged.

  6. EventHandler records the undo step and the new LastFill, then answers with RspMakeBet. It has accepted, the betId, and for a change it has changed and the previousAmount. A refusal has the reason.

  7. The View updates the player area from the events and the OperationManager closes the dialogs on the response. A refusal is shown to the person in an error dialog and nothing has changed.

Odds are a second request, ReqOddsBet, on a bet that already has its number. It goes through Player::setOddsAmount(), and the table checks it against the odds rules. Taking a bet down is ReqRemoveBet. The player’s money comes back to the player.

Betting Rules

  • Bets can be made, changed and removed only while betting is open. The table refuses at the lowest level, so no path can get around it.

  • The limits, the increments and the odds allowed are the table’s. See Model Overview.

  • A Pass Line or Come bet that has a number must stay on the table until it is decided, and its contract amount cannot be reduced. A Don’t Pass or Don’t Come bet that has a number cannot be increased, but it may be reduced or taken down.

  • A request is all or nothing. When it is refused nothing has changed, and the answer says why in words the person can read.

  • The View may know the answer before it asks, but the table decides. A disagreement is settled in favor of the table.

Betting Persistence

Bets are not kept between games. When the game ends, or the table is left, every seated player’s session ends: the bets come down and the money goes back to the player. What is saved is the player’s money and statistics. See Players and Buddies and Persistence and Configuration.

Betting Related Features

  • Bet Automation places many bets in one step, through the same path.

  • Bet Flags set whether a bet works and for how long.

  • Undo of Bet Changes takes back what this page puts on the table.

  • Table Switching takes the bets down when the table is left.

Bet Automation

Automation Purpose

Three features place bets for a player without the player entering each bet by hand:

  • QuickBets: a named bundle of bets that the user applies with a key.

  • AutoOdds: odds that are placed automatically on a contract bet when it becomes eligible for them.

  • Automated bets: bets that a buddy player places on its own, according to a plan. Buddies are the main reason for this feature, and it is not built yet.

They differ in when they act, not in what they do. All of them turn a list of bets into bet requests for a player. This section describes the one mechanism they share, so that the parts built first, QuickBets and AutoOdds, are the parts that buddy automation will need.

The earlier AutoFill and single QuickBet features are removed. LastFill covers what AutoFill did, and a QuickBets entry holding one bet covers what a single QuickBet did.

Automation Vocabulary

Bet spec

One bet to place: the bet name, the pivot if the bet has one, whether it is an odds bet, and an amount. This is what QuickBetEntry and AutoFillEntry already were, as two copies of one struct.

Bet plan

A named, ordered list of bet specs. A QuickBets entry is a bet plan.

Trigger

The moment something is applied. Manual (the user presses a key), betting opened after a roll, come-out, point established, and so on.

Rule

A trigger joined to an action: apply a bet plan, or apply the AutoOdds settings. Only rules for buddies need a general form.

Automation Participants

  • BetExecutor (Controller) applies a list of bet specs for a player and reports what happened. It is the only place that turns specs into bets.

  • QuickBets (Controller) holds a player’s bet plans. Plain data, one per player, held in PlayerPrefs, as the older classes were.

  • AutoOdds (Controller) holds a player’s odds multiples and the master switch, also in PlayerPrefs, and decides which bets need odds.

  • EventHandler receives the requests from the View, calls the executor, and watches for the trigger events for AutoOdds.

  • UndoManager records each application as one undo step.

  • The View has the dialogs: a picker to apply a QuickBets entry, the Set or Add dialog and an AutoOdds entry in DialogBetAmount, and management dialogs on the Configuration menu.

Applying a Plan

BetExecutor applies the specs of a plan, or of an AutoOdds pass, in order:

  • Best effort. A bet that cannot be placed is skipped and the rest go on. The player is told what was placed and what was skipped and why, in one summary, rather than an error dialog per bet. This is chosen over refusing the whole plan because a plan made for one table may not fit another table’s limits and multiples, and a plan that places most of its bets is more useful than one that does nothing.

  • Set, not add. A player has at most one bet per spot. A spec for a spot that already has a bet sets that bet to the spec’s amount. A spec whose amount equals the bet’s amount changes nothing and is counted as already in place.

  • Order. In a plan, a contract bet is placed before the odds on it. Odds specs are limited to PassLine and DontPass odds, whose point is implied. Odds on a Come or DontCome bet exist only after the bet has moved to a number, so they are handled by AutoOdds and cannot be saved in a plan.

  • Same paths as the View. Each placement goes through the same Player::makeOrChangeBet and setOddsAmount that bet requests use, so all the table’s rules, limits, funds checks and events apply unchanged. The player’s balance and the screens follow from the usual events.

  • One undo step. The placements of one application are recorded with undoJoinsPrevious, so a single undo takes back the whole application. This holds for automation too: pressing undo right after a roll takes back what AutoOdds did for that roll.

  • Summary. The result lists, for each spec, placed, changed, already in place or skipped with the reason. It goes to the View as an event. The View puts a short line in the Message area when there is one, and the handler always writes it to the log.

Automation Request Flow

For QuickBets, as built:

  1. MenuBetting q calls OperationManager::applyQuickBets(), which reads the entries with CrapsReaders::readQuickBets() and shows them in DialogPicker. The pick list carries each entry’s name, so the request still names the right entry if the list changes.

  2. The pick sends ReqApplyQuickBets (player id and entry name).

  3. EventHandler::onReqApplyQuickBets() refuses when betting is closed or the entry is not found. Otherwise it calls BetExecutor::apply() with the player, the entry’s specs, UndoManager and the player’s LastFill, and always answers with RspApplyQuickBets.

  4. The response carries the counts, a headline such as “3 placed, 1 skipped” and one line for each skipped bet. accepted means the entry was applied, even if some bets were skipped. A refused request has an error instead.

  5. OperationManager::onRspApplyQuickBets() unwinds the menus, and shows a notice only when something was skipped.

The bet and balance events that the placements cause redraw the screens in the usual way. The View does not need to know which bets were placed.

Saving a bet into QuickBets, as built:

  1. DialogBetAmount q puts the typed amount into CarrierBet and calls OperationManager::quickBetsSetOrAdd(). That makes a BetSpec from the carrier. Line odds get pivot 0, because they sit on the line bet. A bet that cannot be saved, such as Come odds, is refused with a notice.

  2. DialogQuickBetsSetAdd offers a new entry (1) or the existing entries (a, b, …). It reports with OperationManager::onQuickBetsChoice(). A new entry asks for a name in DialogTextInput, whose validator uses QuickBets::checkName() and refuses duplicates ignoring case.

  3. ReqEditQuickBets carries the action (create or add), the name and the spec. EventHandler::onReqEditQuickBets() calls QuickBets::create() or QuickBets::addBet(), which return “” or the reason, and always answers with RspEditQuickBets.

  4. On success the View shows the response’s message in a notice. The player is back at DialogBetAmount, since the operation has no menus to unwind.

Managing entries, as built. MenuConfigure q calls OperationManager::manageQuickBets(). It is a chain of steps, each of which pops itself and reports back, so manageStep_ says which one answered:

  1. Pick the entry in DialogPicker.

  2. Pick the action: rename, change an amount, remove a bet or delete.

  3. Depending on the action: a name in DialogTextInput, a bet in DialogPicker and then an amount in DialogTextInput, a bet to remove in DialogPicker, or a confirmation in DialogConfirm.

  4. One ReqEditQuickBets with the action’s fields (newName, index and amount). QuickBets::rename(), setAmount(), removeBet() and removeEntry() each return “” or the reason, and the response carries the message.

The entry is named in the request, and the bet by its position in the entry. Nothing else changes entries between the pick and the request, so the position is still right. If it is not, the controller refuses with “That bet is no longer in the entry”. An entry keeps at least one bet. Creating an entry and adding bets stay in the bet amount dialog, where the bet is already chosen.

The entries live in PlayerPrefs and are written to the player file when the players are saved, as for Last Fill. No lock guards them. They change only in answer to the View’s own request, and the View reads them only before or after that request, so the two do not overlap until buddy automation reads them from another thread.

QuickBets Rules

  • A QuickBets entry has a name chosen by the user and a list of bet specs. The View shows the name and a generated description of the bets.

  • At most 20 entries and 12 specs in an entry, so that the lists fit the screen and each entry can have a letter key.

  • The Betting menu key q shows the entries to apply. The Configuration menu lists, creates, renames, adds to, trims, changes the amounts of and deletes entries.

  • DialogBetAmount has q for “QuickBets, set or add”. The dialog then offers “Set as new QuickBets entry”, which asks for a name, or “Add to an existing entry”. Adding a spec whose spot is already in the entry replaces the amount, which matches one bet per spot.

  • Amounts are fixed dollar amounts, validated when applied. They are not converted when the table changes.

  • Order of the entries matters and is kept in the player file.

AutoOdds Rules

AutoOdds places odds on a contract bet for the user, in a size that depends on the kind of bet and the point it is on.

  • Settings. A table with an entry for each of PassLine, DontPass, Come and DontCome and each of the points 4, 5, 6, 8, 9 and 10. An entry is either a multiple n, so the odds amount is n times the contract amount, or an exact dollar amount. A missing entry means no automatic odds for that bet type and point. This is needed because odds size depends on the point as well as on the bet. A player may want much more behind a DontPass bet on the 10 than on the 6. Typical examples are 3, 4 and 5 times for the 4 and 10, the 5 and 9 and the 6 and 8. The Configuration menu offers that as a preset and can also set one multiple for every point of a bet type.

  • Master switch. There is one on and off switch for each player, so AutoOdds can be paused without losing the table of multiples. When it is on, the View shows a visible indicator, and each automatic placement is reported in the Message area, since the feature spends the player’s money unprompted.

  • When. AutoOdds runs on UslBettingOpened, after the roll’s results are settled. It looks at the player’s bets rather than following events, so it does not matter whether the bet became eligible because the point was set, a Come bet traveled to a number, or the table was switched.

  • Which bets. A contract bet that has a point or pivot, has no odds, and has not been handled by AutoOdds before. The controller remembers the ids of the bets it has handled. This is needed so that odds the player takes down by hand stay down. Without it AutoOdds would put them back after the next roll. The set is pruned of ids that are no longer on the table.

  • Amount. The exact amount, or n times the contract, rounded down to the table’s required odds multiple and not above the table’s maximum odds for that bet. The table already knows both, from its odds limit rules. If the result is below one odds increment, the bet is skipped and the reason is reported.

  • Failures. Insufficient funds or a refusal from the table skips the bet. AutoOdds does not retry within the same pass. It has already marked the bet as handled.

  • From DialogBetAmount. a sets the entry for the bet type and point of the odds bet being entered to the exact amount entered, and reports it. A zero amount removes the entry. The line is shown only when the dialog is for an odds bet and is blank otherwise, so that the dialog does not change shape.

As built:

  • AutoOdds holds the multiples, the on and off switch and the handled ids. AutoOdds::plan() is the pass. It takes candidate bets, each with the table’s odds limits already looked up, so it is tested without a table. EventHandler::onUslBettingOpened makes the candidates from the user player’s bets, applies the plan with BetExecutor::apply and publishes UslAutoOddsApplied.

  • A bet is marked handled as soon as the pass has a multiple for it, whether or not the odds could be placed. A bet that already has odds is also marked, so odds the player later takes down stay down.

  • AutoOdds is applied for the user player only. Odds are not LastFill entries, since the player did not choose them.

  • ReqEditAutoOdds and RspEditAutoOdds carry every change: the switch, one entry or all points of a bet type (a point of 0), the 3-4-5 preset and clearing. The Set or Unset of DialogBetAmount is a Set with the entered amount.

  • Until the Message area exists, the middle of the bottom bar shows AutoOdds on while it is on, and AutoOdds: n placed after a pass until the next roll. Odds that could not be placed are listed in a notice, unless the player is in the middle of another dialog; the log has them all.

Buddy Automation

Not built yet. This is what the other parts are shaped for.

  • A buddy is an ordinary player with its own PlayerPrefs. Its plans, AutoOdds and rules are kept in that file, as the user’s are.

  • A rule is a trigger and an action. The first triggers are betting opened with no point (come-out), betting opened with a point, and betting opened after any roll. The actions are to apply a named plan, or to apply AutoOdds. Conditions such as the player’s balance and progressions that change amounts after wins and losses come later and fit between the trigger and the action.

  • EventHandler runs the rules for every player that has them at the same UslBettingOpened, through the same executor.

  • A buddy’s undo stack is never used. It is cleared at each roll as every stack is, so it cannot grow.

Automation Persistence

In the player file under Prefs. QuickBets replaces the old one-bet form of the same name, and AutoFills is gone. pivot and isOdds may be left out, and default to 0 and false:

QuickBets:

    bets:
      - { betName: Place, pivot: 8,  amount: 24 }
      - { betName: Place, pivot: 9,  amount: 20 }
      - { betName: Place, pivot: 10, amount: 20 }
  - name: Line with odds
    bets:
      - { betName: PassLine, amount: 10 }
      - { betName: PassLine, isOdds: true, amount: 30 }
AutoOdds:
  enabled: true
  multiples:
    PassLine:
      4: 3x
      5: 4x
      6: $50

Loading follows the Prefs rules already in force: an entry that cannot be read is logged and skipped, and loading never throws. A loaded plan is made valid by QuickBets::tidy(): bets with no usable bet name or a zero amount are dropped, odds on bets other than PassLine and DontPass are dropped, a later bet for the same spot replaces the earlier, contract bets are moved before odds, and a plan is cut to 12 bets. A plan with no name or no bets left is skipped. Old-form entries, which have no name, are skipped the same way.

Automation Related Features

  • Betting is the path that every automated bet goes through, so the table’s rules and limits apply to it unchanged.

  • Undo of Bet Changes takes back everything one QuickBets or AutoOdds application placed, as one step.

  • Players and Buddies keep the plans and settings in their preferences. Buddy automation is the part not built yet.

  • Table Switching can leave a saved amount below the new table’s minimum. The game reports the bet as skipped and the person changes the plan if they wish.

Bet Flags

Bet Flags Purpose

A bet flag says whether a wager is live for the next roll. A live bet can win or lose on the roll. A bet that is not live stays on the table and neither wins nor loses. Casinos let a player call certain bets off and on at any time, and the flags give the player the same control.

Two things are controlled, for one bet or for a category of bets:

  • A standing state, which lasts until the player changes it.

  • A one-roll override, which applies to the next roll only and then goes away, leaving the standing state as it was.

Bet Flag Vocabulary

Standing state

One of Default, Working and Off.

Default is the house rule that is in force today. Place, Buy, Lay and odds bets are not live on a come-out roll and are live on every other roll. Hardway bets are live on every roll. A bet starts as Default.

Working means live on every roll, including come-out rolls. Off means not live on any roll until the player changes it.

One-roll override

One of None, Off next roll and Working next roll. Off next roll makes the bet not live on the next roll whatever its standing state is. Working next roll makes it live on the next roll, for example a Place bet that the player wants working on the coming come-out. The override is cleared after every roll, and a bet starts with None.

Live

A bet is live on a roll when the override says so. With no override, Working is live, Off is not, and Default follows the house rule above.

Category

A group of bets that a flag change can be applied to together: All, Odds, Place, Buy, Lay and Hardways.

Bet Flag Participants

  • CrapsBet holds the standing state and the one-roll override and answers whether it is live on a roll.

  • CrapsTable::setBetFlags() is the one way to change flags in the running game. It checks legality and that betting is open, then publishes the bet changed event. Player::setBetFlags() is the player’s side of it.

  • BetFlags (in the Controller) names the scopes and the changes, says which bets are in a scope, and turns a change into a new state.

  • EventHandler answers ReqSetBetFlags with RspSetBetFlags and records the undo group.

  • UndoBetFlagsChanged keeps the previous state of one bet.

  • MenuBetFlags and OperationManager run the menus and the request.

Bet Flag Legality

Flags follow casino practice, so they are accepted only for bets that a player may legally call off and on:

Bet

Flag allowed

What the flag controls

Odds on Pass Line, Don’t Pass, Come, Don’t Come

Yes, when there are odds

Only the odds. The contract bet is always live.

Place, Buy, Lay

Yes

The whole bet.

Hardway

Yes

The whole bet.

Pass Line, Don’t Pass, Come, Don’t Come contract bets

No

Not applicable; a player cannot call these off.

Field, Any Craps, Any Seven, Any 7 or 11, C and E, Horn, World

No

They are decided on the next roll, so there is nothing to call off.

The table refuses a flag change that is not legal, and refuses any change when betting is closed, with the same errors it gives for other illegal bet changes. Changes that apply to a category skip the bets that cannot take a flag, and the response says how many were changed and how many skipped.

Bet Flag Rules in the Model

CrapsBet holds the standing state and the one-roll override in place of the single offComeOutRoll_ flag. It answers one question, whether it is live on a roll given the point, and the evaluation functions use that answer in place of testing point == 0 && offComeOutRoll_.

  • Place, Buy, Lay and Hardway are Keep when not live, and are decided as they are today when live.

  • Odds on a contract bet follow the same answer. Today the odds are returned when they are off on a come-out roll that decides the bet. The same happens whenever the odds are not live on the roll that decides the bet: the contract bet wins or loses as usual and the odds go back to the player without a win or loss.

  • The existing setOffComeOutRoll, setOnComeOutRoll, setHardwayOff and setHardwayOn stay, so existing code and tests keep working. They set the standing state: Default for the first and the fourth (a Hardway that is Default is working), Working for the second, Off for the third. offComeOutRoll() and hardwayWorking() remain as observers and answer for the standing state with no override.

  • CrapsTable clears every bet’s one-roll override after it resolves the roll, before betting opens again.

  • A change to a standing state replaces the bet’s one-roll override: the Controller sends both together, so “Set Working” leaves no override behind. A “Next Roll” change leaves the standing state alone. Taking the odds off a bet takes its flags with it.

  • CrapsTable::setBetFlags is the only way to change flags in the running game. It checks legality and that betting is open, then publishes the same bet changed notification that an odds change does, so the screens redraw. Flags are not saved with the player, since bets are not.

The Bet Flags entry of the Betting menu (g) opens a menu of categories. A category appears only if the player has bets on the table that can take a flag in it, and the whole menu is refused with a notice if there are none.

Bet Flag Workflow

Every choice sends one request and shows the answer:

  1. The View sends ReqSetBetFlags with the player, a scope (one bet, All, Odds, Place, Buy, Lay or Hardways), the bet id when the scope is one bet, and the change (Not-Working, Not-Working Next Roll, Working, Working Next Roll or Table Default).

  2. The Controller applies it through CrapsTable::setBetFlags for each bet in scope that can take it, as one undo group, and answers with RspSetBetFlags: accepted or an error, a message such as “Odds bets set Not-Working: 2 changed”, and the counts.

  3. On success the View unwinds the menus and shows the message in a notice. On failure an error dialog says why, as for other bet requests.

Bet Flag Undo

A flag change is undoable with the Undo key. UndoBetFlagsChanged keeps each bet’s previous standing state and override, and restores them through CrapsTable::setBetFlags, so the table checks the bet and the events are published. The undo stack and its rules are unchanged: it is cleared when the dice are rolled.

Bet Flag Display

The amounts in the player’s bet area are bold, in the player’s color. A bet that is not live on the next roll is drawn dim instead, and a bet that has a standing state other than Default or has an override is underlined. So a Place bet that is Off shows dim and underlined; a Place bet set to Working next roll shows bold and underlined until the roll, and a Place bet with no flags shows dim on the come-out, by the house rule, and bold otherwise. No room is taken, so large amounts are not affected. The bet dialogs already say that a bet is off on the come-out roll by default, and that text is kept. If a terminal cannot dim, the bet is shown without bold.

Bet Flag Persistence

None. Flags belong to a bet, and bets are not saved between games, so a new bet always starts as Default with no override.

Bet Flag Related Features

  • Betting makes the bets that carry the flags.

  • Undo of Bet Changes takes back a flag change.

  • Bet Automation does not set flags. A bet it places starts as Default.

Undo of Bet Changes

Undo Purpose

A player can take back bet changes made since the last roll: a bet placed, a bet’s amount or odds changed, or a bet taken down. Undo is limited to bets. Settings, rolls and the state of the game are never undone.

Undo Vocabulary

Step

One recorded change that Undo takes back at one press. It is one bet change, or a group of them.

Group

Several changes taken back together. One QuickBets application, one flag request and one AutoOdds application are each a group.

Stack

A player’s steps, last in first out.

Undo Participants

  • UndoBet is one recorded change that knows how to take itself back and how to describe that in words. Its subclasses are UndoBetAdded, UndoBetRemoved and UndoBetModifiedAmount. UndoGroup holds several as one step.

  • UndoManager is a singleton holding a stack of steps for each player.

  • EventHandler records a step after every bet request that succeeds, answers ReqUndoBet with RspUndoBet, and clears the stacks when a roll is requested.

  • Player and CrapsTable provide the restore paths that undo uses: Player::restoreBet(), Player::restoreAmounts(), and CrapsTable::restoreBet() and CrapsTable::restoreBetAmounts().

  • OperationManager runs the Undo operation for MenuBetting.

Undo Recording Steps

The View knows nothing of the stack. The recording happens entirely in the Controller, so any View, and later any automation that goes through the same requests, is undoable the same way.

  • ReqMakeBet for a spot with no bet records UndoBetAdded. For a spot that already has a bet the request changes the bet’s amount, which records UndoBetModifiedAmount if the amount really changed. A UndoBetModifiedAmount is built before the change, because it copies the bet’s state as it is then.

  • ReqOddsBet records UndoBetModifiedAmount, whether it sets, changes or takes down odds.

  • ReqRemoveBet records UndoBetRemoved. The stack keeps a shared pointer to the removed bet, which is what lets it be put back.

  • A change that is refused records nothing.

  • Taking down several bets at once sends one request per bet. All but the first carry undoJoinsPrevious, which makes UndoManager merge the change into the step on top of the stack, wrapping that step in an UndoGroup first if it is not one already. The batch is then undone in one step, last removal first.

Undo Restore Paths

Undo does not run a change backward through the normal bet functions. The change being undone was allowed, and undoing it can look like a change that is not: reducing a PassLine bet after the point, increasing a DontPass bet, or putting back a DontPass bet after the point. The normal rules would refuse these.

The restore paths therefore skip the rules for making or changing a bet, and check only what must be true for undo to be safe: betting is open, the bet is on the table (or, for a restore, is not already there) and the player has the money. They go through the table, so the player’s wallet, the house bank, placement commission and the bet, balance and table events all update as for a normal change. Without those events the screens would not follow the undo. The bet’s original id is kept, so the screens treat a restored bet as the same bet.

A bet placed by the player is taken down the normal way by UndoBetAdded, through Player::removeBet(), since that is what it is.

Undo Rules and Limits

  • Last in, first out. There is no random access and no redo.

  • Each player has a stack, and an undo request applies to its own player. The View asks for the user player. This keeps the bets of a buddy safe from the user’s undo, and a player who switches away and back keeps their steps.

  • The stacks are cleared when a roll is requested, because the roll decides the bets, when the table is switched, and when a buddy leaves the table. They are cleared before the roll, in the request handler, so the clearing is ordered with the bet requests and no timing between threads is involved.

  • Undo is refused while betting is closed. The refusal keeps the steps.

  • A failed undo drops that player’s whole history and reports the reason. The step that failed is no longer known to match the table, so undoing the steps below it would be unsafe. Nothing is changed by the failed step itself.

  • A mutex protects the stacks, since requests and tests may use them from different threads.

Undo Workflow

MenuBetting calls OperationManager::undoLastBet() for u. The operation sends one ReqUndoBet for the user player and waits for the RspUndoBet with the matching correlation id.

  • Success: the betting menus unwind to the table screen, as after any bet. The bet and balance events that the undo caused have already been sent, and redraw the player areas and the balances as they do for any bet change. The response carries a description such as “Took down your $10 Place 6 bet”, which is logged.

  • Failure: an error dialog shows the reason. Nothing to undo and betting closed are the common ones. After the player acknowledges it, the menus unwind.

Changes to a bet’s flags are recorded. One flag request is one undo group, made of one UndoBetFlagsChanged for each bet that changed. It keeps the bet’s previous standing state and one roll override, and restores them with Player::setBetFlags, which goes through the table so the checks and events happen. See “Bet Flags”. The earlier UndoBetModifiedFlags class was removed because it restored a bet by overwriting it, which skipped the table and its events.

Undo Persistence

None. The stacks live in memory only. They are cleared at every roll, so a game never has anything to undo at the start.

Undo Related Features

  • Betting records a step for each bet it makes, changes or removes.

  • Bet Automation records one group for each plan or AutoOdds it applies.

  • Bet Flags records a group for each flag request.

  • Table Switching and a buddy leaving the table clear the stacks.

Players and Buddies

Players and Buddies Purpose

Up to six players share a table. One of them is the user player, the one the person at the keyboard is playing as. The others are buddy players who come with the game and sit at the table for company. Players keep their money, their bets’ statistics and their preferences from one game to the next.

Players and Buddies Vocabulary

Term

Meaning

User player

A player the person can become, rename and delete. The person may make as many as they like. A new player is always a user player.

Buddy player

A player delivered with the game. A buddy can sit at the table and leave it, but never becomes the user player and is never renamed or deleted.

Manifest

The index of the players, with the id, kind, name, description and file name of each.

Preferences

What the game remembers about a player apart from the player’s money: QuickBets, AutoOdds, LastFill and, for the user player, whether the buddies follow to a new table.

Session

The time a player is at a table. It ends when the player leaves or the table is left, and its results are added to the player’s history.

Players and Buddies Participants

  • PlayerManager knows who the players are, loads them, owns their files and preferences, and knows who the user player is. It is the one place that creates, renames, deletes and switches players.

  • PlayerManifest is the index. It is read and written as one file.

  • Player is the Model’s player. It converts itself to and from YAML and knows nothing of files. See Model CRC Cards.

  • PlayerPrefs holds the preferences and is saved with the player, in its own section of the player’s file.

  • EventHandler answers ReqManagePlayer and ReqSwitchPlayer.

  • MenuPlayers and OperationManager run the operations for the person: pick a player, confirm, send the request, show the answer.

Players and Buddies Flow

Starting. The manifest is read, and the players named in the starting choices are loaded from their files and seated. The user player is the one named in the saved state. See Startup, Shutdown and Directory Layout.

Switching the user player. ReqSwitchPlayer names the player to become. PlayerManager::switchPlayer() checks that the player is known, is not already the user and is not already at the table, and loads the player if needed. The table then swaps the two players. The old user’s session ends, the old user’s bets come off the table and the money goes back to the old user, and the new user takes the seat and the dice if the old user had them. The player who left is written to his file. If anything fails before the swap, nothing has changed and the old user is still playing. The View asks the person to confirm first if there are bets on the table.

Managing players. ReqManagePlayer carries an action.

  • Create makes a user player with a fresh id, a name, an optional short description and the usual starting bank. The player file and the manifest are written at once. It does not switch to the new player.

  • Rename changes the name. Names are trimmed, 1 to 16 printable ASCII characters and unique ignoring case. Only the name changes. The id and the file name stay, because the saved state refers to players by file name. The manifest is written at once.

  • Delete applies to a user player who is not the current user and is not at the table. The file is moved to a trash folder and not erased.

  • BuddyJoins and BuddyLeaves seat a buddy or take one away. A leaving buddy’s bets come off the table and the money goes back to the buddy.

Each is answered by RspManagePlayer. When it succeeds the table and the player publish the usual events, and a rename also publishes UslPlayerRenamed so that the View drops the names it kept.

At a new table. When the user switches tables, BuddyFollow decides what the buddies do: Follow takes them along, Stay leaves them out, and Ask has the View ask the person at the time. See Table Switching.

Players and Buddies Rules

  • At most six players sit at a table.

  • A player is at one table at a time, and has at most one bet for each spot.

  • The user player and buddy players are told apart by kind in the manifest, and the kind is checked by the manager, not trusted from the View.

  • The manager’s lists are guarded by a mutex. getPlayers() hands out a reference and is not protected, so it is not to be called while a switch can be running.

  • A player who is switched out stays loaded. If he is switched in again he starts a new session.

Players and Buddies Persistence

Each player has a file in the players folder, with a section for the player and a section for the preferences. The manifest is a separate file. The player files are written when the game ends, when the user player switches, when a player leaves the table or the table is switched, and when a preference such as buddy follow is changed. A rename or a new player writes the manifest at once and the player’s file at the next save moment. Session results are merged into the player before the player is saved, so the manager always saves after the table has shut the players down.

Players and Buddies Related Features

  • Table Switching moves the players to another table.

  • Bet Automation keeps its settings in each player’s preferences.

  • Statistics are kept for each player and for each table.

  • Buddy players that place bets of their own are not built yet. The buddies now sit and watch.

Table Switching

Table Switch Purpose

The game comes with several tables, listed in tables.yaml. The user player can move to another one during play, with or without the buddy players. The tables are fixed by the installation. Making a table is not a function of the game.

Table Switch Vocabulary

Manifest

tables.yaml, the list of the tables that come with the game, with a name and a file for each.

Table file

The file of one table. It holds the table’s rules and the table’s own statistics and session history.

Buddy follow

The user player’s choice of what the buddy players do on a switch: Follow, Stay or Ask.

Retired table

A table that has been switched away from. It is closed and empty, and is kept until the game ends so that a late read by the View is safe.

Table Switch Participants

  • TableManager owns the current CrapsTable and the file it came from. switchCrapsTable() does the whole switch. CrapsTable knows nothing of files.

  • EventHandler answers ReqSwitchTable with RspSwitchTable, then sends UslTableSwitched and the new table’s snapshot events.

  • BuddyFollow (Follow, Stay, Ask) is kept in PlayerPrefs with the user player. ReqSetBuddyFollow changes it. With Ask the View asks, then sends the answer in ReqSwitchTable.

  • OperationManager runs the Table operations for MenuTable, and the Buddies Follow choice for MenuConfigure.

Table Switch Steps

  1. Check: the table is in the manifest, is not the current one, and betting is open. Load the new table file. A file that cannot be read fails the request and nothing has changed. After this point the switch does not fail.

  2. Every seated player ends the session at the old table: bets come down, the money is returned and statistics are merged.

  3. The undo stacks are cleared. The old table is closed, which records the session with the number of players it had, and its file is saved.

  4. The new table becomes Gbl::pTable. The user player and, if they follow, the buddies join it in the seating order they had. The user is the shooter.

  5. The players’ files are saved and AutoOdds forgets what it handled.

The old table object is retired, not deleted. The View reads the table directly through CrapsReaders, and it may be in the middle of a read on the CUI thread as the switch happens. A retired table is closed and empty, so a late read is safe. Retired tables are released when the game ends.

On UslTableSwitched the View clears the roll list, resets the title bar and the dice window, and refreshes the roster. The numbers for the house and the players arrive in the snapshot events that follow it.

Table Switch Rules

  • Only a table in the manifest can be switched to, and not the table the player is at.

  • Switching is refused while betting is closed, that is, during a roll.

  • The new table is loaded before anything is changed. If its file cannot be read, the request fails and the player is still at the old table.

  • A player’s bets do not go along. They come down and the money returns to the player, as when a player leaves a table.

  • A player’s saved QuickBets, LastFill and AutoOdds are not changed for the new table. An amount that is too small for the new table is refused when it is used, with the table’s reason, and the person may change it.

Table Switch Persistence

The old table’s file is saved when it is closed, with its statistics and the session just ended. The players’ files are saved after the switch. Which table the game starts at next time is part of the saved state. See Persistence and Configuration.

Table Switch Related Features

lib-gen is a C++ library of general purpose, cross cutting design elements. Nothing in it knows about craps, and no other project library is below it. ErrorPass

ErrorPass CRC Card

An error, carried as a value.

Responsibilities

  • Describe a failure: an error name, an error type, a severity and a description, with an optional probable cause, proposed repair and additional information.

  • Say where it happened: the function, file and line where it was set, and a time stamp.

  • Grow as it travels. Each caller may prepend or append words to the description, or add its own place to a stack trace, so that the error tells the whole story when it is finally shown.

  • Be extended by the application. Error names and types are strings. A standard set covers common cases, and an application may use its own words without deriving a class.

  • Say whether it is set. An empty error name means no error.

An ErrorPass is used in two ways. In the value-based way, a function returns zeus::expected<T, ErrorPass>, which holds either the value or the error. In the call-chain way, the caller declares an ErrorPass and hands it down, and the callee fills it in only if it fails. The macro EP_SET sets an error with the place filled in, and EP_TRACE adds the current place to the trace.

Collaborators

  • zeus::expected: the carrier in the value-based way

  • Logger: errors are logged with fullDesc()

  • ReturnCode: the result of call-chain functions

  • Every library: the Model refuses a bet with one, and the Controller puts one in a response event for the View to show

EventManager

EventManager CRC Card

An asynchronous publish and subscribe bus.

Responsibilities

  • Take subscriptions. A handler is subscribed for one event type. Any number of handlers may be subscribed for a type.

  • Take events. publish() copies the event into a queue and returns at once, from any thread. It does not run a handler.

  • Deliver events. A single worker thread takes the events in the order they were published and calls each handler for the type. Handlers run one at a time on that thread, so one that blocks holds up all that follow.

  • Finish what was queued. At shutdown, events already queued are delivered before the manager ends. A publish after shutdown has begun throws.

  • Hold subscriptions for life. There is no unsubscribe.

The queue and the subscriber map are protected by one mutex. Handlers are copied under the lock and called after it is released, so a handler may subscribe or publish without deadlock.

Collaborators

  • Every publisher and subscriber, by event type

  • GameEvents (Controller) defines the types the game uses. See Events.

Logger

Logger CRC Card

One log for the whole program.

Responsibilities

  • Write log lines with a time stamp and a level. The levels are debug, trace, info, warn and error.

  • Write to a file, and to the console until the console is turned off. Console output is in color by level.

  • Hold early messages. A message logged before there is an output file is formatted at once, so its time stamp is true, and held. The next output file gets them first. At most 1000 are held.

  • Switch the extra levels. Debug and trace messages are compiled in only in a debug build, and are written only when switched on.

  • Be safe from any thread, with a mutex.

The macros LOG_DEBUG, LOG_TRACE, LOG_INFO, LOG_WARN and LOG_ERROR are what the code uses.

Collaborators

  • rang: the console color

  • ConfigManager (Controller): the log.debug and log.trace settings

  • GameMain (Controller): sets the file, and turns the console off before the screen starts

TimerManager

TimerManager CRC Card

Many timers on one thread.

Responsibilities

  • Make timers, armed at once or armed later. A timer has an id.

  • Fire timers. A timer fires once, or repeats and re-arms itself.

  • Cancel and restart a timer by its id, at any time.

  • Run every callback on one dedicated thread. All calls are thread safe.

A callback runs on the timer thread, so it has to be short and has to leave the data of other threads alone. The game’s callbacks only queue a request for the thread that owns the data.

Collaborators

  • WindowAnimation (View): creates the dice animation timer, and its callback queues the drawing for the CUI thread

MultiLayerConfig

MultiLayerConfig CRC Card

Settings from several places, read as one.

Responsibilities

  • Hold named layers. Each layer is a map of keys to string values. The standard layer names are defaults, files, env and cmdline. An application may add others.

  • Resolve a key. The layers are searched from the last one added to the first, and the first layer that has the key wins. So the order the layers are added is the order of priority.

  • Convert on the way out. getInt and getBool convert the text, and answer nothing if it does not convert. getBool accepts true, false, yes, no, on, off, 1 and 0 in any case.

  • Export the resolved settings, one value for each key.

  • Be safe from any thread, with a mutex.

Collaborators

  • ConfigManager (Controller): adds the game’s layers, including a session layer on top, and fills them. See Persistence and Configuration.
